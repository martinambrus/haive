# CLI adapter system

`packages/worker/src/cli-adapters/base-adapter.ts` defines `BaseCliAdapter`. Implemented adapters: `claude-code`, `codex`, `gemini`, `amp`, `zai`, `antigravity`, `ollama`, `muse`, `grok`, `openrouter`. Each declares `supportsSubagents`, `supportsCliAuth`, `supportsMcp`, `supportsPlugins`, `defaultAuthMode` (`subscription` or `api_key`), and `apiKeyEnvName`. `supportsSteering` defaults to false; the Claude-family adapters (`claude-code`, `zai`, `ollama`, `muse`, `openrouter`) override it to true, and so do `amp` and `codex` — codex only through its app-server, and only once that is verified for the task (`steeringTransportReady`) — see [Steering](steering.md).

Four adapters are the same trick: the stock `claude` binary pointed at a non-Anthropic Anthropic-wire endpoint via `ANTHROPIC_BASE_URL` — `zai` (api.z.ai), `ollama` (in-stack daemon or ollama.com), `muse` (api.meta.ai), `openrouter` (openrouter.ai/api). All four piggyback the `claude-code` install, so they build no new sandbox image. Their per-endpoint quirks are MEASURED against the live API and recorded in the adapter, not taken from vendor docs — `muse` exists as its own adapter purely because its effort scale rejects `max`, and `openrouter` records the opposite finding (its effort enum is validated globally at the gateway, so every level is safe on every model). Re-probe before "correcting" any of those comments.

`ollama` records the third effort finding, and it is the only scale in the codebase whose default is not its top level: `low|medium|high|max` with default `high`. The level arrives as Anthropic `output_config.effort`, which Ollama's compat layer reads only because the claude binary sends `thinking:{"type":"adaptive"}` — the layer honors `thinking.type` for the literals `enabled`/`disabled` and falls through to effort for anything else. An out-of-range level never 400s; it leaves the think value unset, which Ollama then forces on for a thinking-capable model. `max` is exposed but not the default because gpt-oss does not recognise it as a harmony level and reasons LESS at `max` than at `high`, and deepseek-v4-pro at `max` spent an entire output budget in the thinking channel and returned empty text — the same failure the disable-thinking proxy exists for. `high` is additionally what the binary already sent before the scale existed, so the default changed nothing. Orthogonally, the level is on/off only for most LOCAL models: every built-in renderer in ollama 0.24.0 reads `think.Bool()` and none reads `ThinkLevel`, while Ollama Cloud models are rendered upstream and honor all four. Do not "correct" this scale to match zai's — re-probe.

`openrouter` traffic goes through the `openrouter-compat-proxy` sidecar (`docker/openrouter-compat-proxy/`), not straight to openrouter.ai. The claude binary appends a trailing `role:"system"` message (the Agent tool's agent-type listing) on top of the top-level `system` field; OpenRouter passes Anthropic models through natively, but every other vendor needs an Anthropic→OpenAI translation in which that message keeps its position, and vLLM-style backends answer `400 "System message must be at the beginning."` (measured on `qwen/qwen3.8-27b` across all three of its upstreams; `--disallowedTools Agent` does not stop the binary emitting it). The proxy hoists it into `system`. Unconditional rather than toggled — the rewrite is a no-op when no such message is present and was verified not to change already-working models — so unlike ollama's thinking proxy there is no per-provider switch. `resolveOpenRouterBaseUrl` is the single place that endpoint is chosen, shared by the adapter and the Test-connection probe; a provider that sets `ANTHROPIC_BASE_URL` by hand bypasses the proxy and the probe then says so.

`openrouter` fronts 400+ models, so the provider form picks from a cached catalog rather than a free-text slug: the worker's `REFRESH_VERSIONS` job also refreshes `openrouter_model_cache` (`cli-versions/openrouter-models.ts`), the API serves it at `GET /cli-providers/openrouter/models`, and the picker refuses models whose `supported_parameters` lacks `tools` because Claude Code cannot run a step without native tool use. The cache is never a gate: an empty or errored catalog degrades to a free-text model field.

`model_identity` (`queues/cli-exec/model-identity.ts`) records which model ANSWERED, not which one was configured. Two DISTINCT channels, not two names for one value: the claude-family stream-json `system`/`init` event carries what the binary ASKED for, each `assistant` event's `message.model` carries what the endpoint SERVED, and they disagree — api.z.ai answers a `glm-5.3[1m]` request as `glm-5.3`, and recorded streams show the same provider served `glm-5.2` on 2026-07-24 and `glm-5.3` on 2026-08-18, i.e. an endpoint can swap models with no config change here. Coverage is MEASURED per provider: `claude-code`/`zai`/`ollama`/`muse`/`grok`/`openrouter` report both channels; `gemini` names its models only as the keys of `stats.models`; `antigravity` names one only in its `--log-file` and only as a human LABEL (`Gemini 3.7 Flash (High)`), parsed from ONE constant marked volatile that returns null on a reword; `amp` and codex's `exec` report NOTHING. codex's `exec --json` carries no model on any typed event (verified against a complete 3.4 MB SUCCESSFUL run — `model_provider` strings found in such a stream come from old `~/.codex/sessions` rollout files an agent happened to read, not from live events), and amp emits `agent_mode` instead because it abstracts the model away. codex exec still records `requested`, read off its own `--model` argument — the adapter passed the short `-m` until 2026-09-13, which the argv reader never matched, and MEASURED, 0 of 624 codex invocations carried any identity. codex's app-server does better on one channel: `thread/start` names the model it resolved, recorded as `requested`, while a served model appears only when it reroutes (`model/rerouted`, source `codex-app-server`). So amp is permanently `match: 'unknown'` and codex nearly always is, which is why `unknown` never fails a run.

Two traps in that data. `result.modelUsage` keys are recorded as `billed` and are NOT an identity source: `grok` serves `grok-4.6` while billing `grok-4.6-build`, and `claude-code` bills a `claude-haiku-*` call for its own session titling. The one thing read from that map is the context window, and it is read by identity (the entry keyed by the init or served model), never by position: see `contextWindow` below. And an `assistant` event with `model:"<synthetic>"` is a message the BINARY authored (an API error), not a model reply — filtered on the angle-bracket convention rather than the literal word, so a future sentinel is excluded too. `requested`/`served` are stored verbatim; only `match` is lenient, and only for one case: an endpoint that DROPS a trailing variant tag while naming the same model (`glm-5.3[1m]` to `glm-5.3`) is `exact`. That keys on the tag's PRESENCE differing, not on tag-stripped equality, so a version swap (`glm-5.2[1m]` to `glm-5.3`) and a different variant (`[1m]` to `[200k]`) both stay `differs`, and ollama's colon marker (`glm-5.2:cloud`) is untouched. A mismatch warns and never blocks — claude-code legitimately resolves an alias to a dated snapshot — unless `CONFIG_KEYS.MODEL_IDENTITY_STRICT` (default false, admin toggle) is on. Capture rides the same parse as token usage, so it costs no extra call, prompt or tokens; the canary (`00-model-health`) then copies the task-default provider's identity onto `tasks.model_identity`, while per-invocation truth stays on `cli_invocations.model_identity` because per-step CLI preferences let one task run several models. Re-measure with `packages/worker/test/model-report-discover.ts` before "correcting" any of this — it runs each adapter's real invocation and feeds the live output through the shipped parser.

`tool_usage` (`cli-executor/tool-usage.ts`) records what a run USED — native tool calls, MCP tool calls (`mcp__<server>__<tool>`, grok's `use_tool`, codex's `mcp_tool_call`), native sub-agent activity, `Skill` calls, and the agent-definition / skill FILES the agent opened — tallied by the same pass as `token_usage` and `model_identity`, so it costs nothing extra, and persisted to `cli_invocations.tool_usage` (migration 0159). Three facts to keep. NULL means "not yet examined"; a written `coverage: 'none'` means "examined, not observable on this path" — amp (MEASURED: its stream-json assistant events carry text blocks only, across all 39 stored runs), gemini (no stream parser), antigravity (unmeasured), plain output and the sequential sub-agent script — the one deliberate departure from `compaction`'s "never write an empty object", because it is what lets the backfill's `IS NULL` predicate converge. Codex items arrive TWICE, `item.started` then `item.completed` (app-server: `item/started`, `item/completed`), so only the completed one counts, and the app-server's camelCase item types are folded onto the exec spellings so one record covers both transports. And a read is classified against the provider catalog's `projectAgentsDir`/`projectSkillsDir` union, matched on whole segments from the sandbox MOUNT ROOT (`/haive/workdir`, never the resolved cwd — a worktree run's cwd sits under `.haive/worktrees/`), with `README.md`, the `-legacy` quarantine and a CLI's own skills outside the tree (`/home/node/.codex/skills`, grok's `bundled/skills`) never counting — nor a glob or shell variable standing where a filename stem should (`cat .claude/agents/*.md` reads every persona or none, and the tally cannot say which; MEASURED, `*` and `$f` once ranked beside real personas). Every CLI naming quirk sits in ONE volatile constant in that module; re-measure against stored rows before "correcting" it. `agents.assigned` is the one field no CLI reports: the dispatcher reads the `[[HAIVE_AGENT_DEFINITION:<id>]]` marker ids off the prompt BEFORE `adaptPromptForCliCapabilities` rewrites them (`agentGuidanceIds`), a mining step whose agent IS a persona names it (`AgentMiningDispatch.personaIds` — 03's roster, whose prompt carries no marker), a prompt step's resolved template personas join it (`promptStepPersonaIds`), and the union rides the spec as `assignedAgentIds` to the completion write, which stamps it on the success and the failure path alike. It cannot be backfilled: the stored prompt is the rewritten one — MEASURED, 0 of 3,476 stored prompts hold a marker, and the 228 that name a `.claude/agents/<id>.md` path are matching the repository file-tree listing in the prompt, not a pointer — so the stats tab says "recorded from" the first stamped row instead of reading an empty list as "unused".

`peakPromptTokens` (an optional field of `CliTokenUsage`, stored in `cli_invocations.token_usage`) is the prompt side of the largest single model request in a run, and it is what a finished step's context badge divides by the window (`step-engine/step-context-usage.ts` writes `task_steps.context_tokens`, `context_window_size` and `context_left_percent`). Every other token field is a run TOTAL: the claude binary's `result` usage counts the re-read cached prefix once per turn, so a 139-message run stored 37,260,946 prompt tokens while its largest prompt was 383,759, and a badge built from the total read 0% on every multi-turn run (MEASURED on the dev install: 96 of 144 claude-code step peaks read 0% left, and in the 12 runs replayed in full the stored figure was exactly the sum of the per-message prompts). Two sources exist, both MEASURED. The claude-family collector (`createStreamJsonCollector`; measured on claude-code, grok and ollama rows, and amp reports per-message usage only) takes the largest `input + cache_read + cache_creation` over the same per-`message.id` usages its killed-run fallback sums; sub-agent messages count, as they do in the CLI's own ledger. codex's app-server takes the largest `tokenUsage.last.inputTokens` of its `thread/tokenUsage/updated` notifications: `last` is the latest request, `total` the running sum of them (31716 + 32261 = 63977 in a recorded run), and codex input already INCLUDES the cached prefix, so nothing is added. Nothing else reports a per-request figure: `codex exec --json` emits one cumulative `turn.completed` over the whole run (up to 184 completed items in the recorded ones), gemini's JSON envelope carries per-model aggregates only, antigravity's `step_update.usage` is unmeasured, and zai and muse put `{input_tokens: 0, output_tokens: 0}` on their assistant events with `result.usage.iterations` empty. Where the collector has no figure the field is ABSENT, never 0, and the three `task_steps.context_*` columns are written NULL, so the badge is empty: a cumulative total is a guess (it read 0% on 143 of the 237 stored steps), and for codex it also double counted the cache, because codex input already INCLUDES the cached prefix (`context_tokens == input + cacheRead` on 62 of 62 stored codex peaks, a median 1.88x too high). The one exception is a run of exactly ONE model request, where the total IS that request's prompt. zai and muse put zero usage on their assistant events, so when the stream holds a single distinct assistant `message.id` and the `result` carries usage, the collector takes that usage as the peak (zai 8c3e3659: 31,333 input + 768 cache read = 32,101). The proof is the message-id count and not `result.num_turns`, which is tool calls + 1 on the claude binary (so it exceeds the message count whenever tools run in parallel) and per turn on a steered run. Nothing proves one request for `codex exec` (one `turn.completed`, one `agent_message` and no tool item held for 45 of 45 tool-free runs, which is an inference on the legacy transport), gemini's `api.totalRequests` appears only in a hand-written fixture and antigravity's `num_turns` is never read, so those stay empty. `writeStepContextUsage` still names the invocation whose allowance the step used by the old weight (the peak where there is one, else the stored totals, which are never shown), and stamps that provider's allowance and returns it for the usage poll whether or not the badge is empty; a re-finalized step also loses a stale figure, because every write that finishes a step (done, failed, skipped, a gate close) nulls the six stamp columns and only a done row is stamped afresh, fenced on its id, `done` and the `ended_at` that write returned; the task page shows the stamp only on a done row (`showsStepUsageStamp`), so a re-opened step never shows the previous attempt's figures, though the api still returns them on an open row. Rows stored before this keep what they were stamped with and were not recomputed: 59 of the 237 stored steps would now be empty (codex exec 54, zai 5; all stamped on 2026-09-12/13). `sumTokenUsage` carries the field as a MAX, since the sequential sub-steps it sums are separate contexts. The window it is divided by is recorded separately, as `contextWindow`.

`contextWindow` (an optional field of `CliTokenUsage`, stored in `cli_invocations.token_usage` beside `peakPromptTokens`; a jsonb key, so no migration) is the context window the CLI ITSELF reported for the model that ran the invocation, and the denominator of the step context badge. It is read where the stream states one and never guessed. The claude-family collector takes `result.modelUsage[<model>].contextWindow` for the model the `system/init` event named, else for the model that served the last assistant message, and for no other entry: `modelUsage` lists every model billed, and the binary's own titling call puts a `claude-haiku-4-5` entry (200,000) beside the main model in 2,411 of the 2,470 stored claude-code logs that report any window, listed FIRST in 2,409 of them, so the first, the smallest, the largest and the only entry are each wrong somewhere. MEASURED on those logs, the init model's entry is the right one in 2,466 of 2,470; the other 4 hold only the haiku entry, on runs whose single assistant message was authored by the CLI, and correctly yield no window. zai names `glm-5.3[1m]` at init and bills that key while the endpoint serves `glm-5.3`, which is why the init name is tried first; grok bills `grok-4.6-build` while naming `grok-4.6`, and its entry carries no window in any of the 14 stored runs. The window rides the `result` event, so a killed run has a peak and no window, and a later result without one never erases an earlier window (a steered run has several, with cumulative `modelUsage`). codex's app-server states `modelContextWindow` beside `total` and `last` in every `thread/tokenUsage/updated` (258,400 in 284 of 284 stored events: 95% of the nominal 272,000), so it is read from the first notification. `codex exec`, gemini and antigravity state none, and amp's `usage.max_tokens` (272,000 in 14 of 14 stored runs) is not taken: nothing documents it and the repository uses the same word for the OUTPUT cap. The key is ABSENT when unknown, never 0 or null (about 15 exact-key-set tests pin that), and `sumTokenUsage` carries the smaller of two windows, since a window belongs to a model and is not additive.

`writeStepContextUsage` divides by the first of: the OpenRouter catalog's `context_length` for the routed model, the peak invocation's `contextWindow`, and only then the table in `shared/src/cli-providers/context-windows.ts`, which is a FALLBACK for the runs that recorded none (killed runs, CLIs that state none, rows from before the key). The catalog outranks the CLI's figure because the claude binary reports its own default for model ids it does not know: ollama's `gemma4:31b-cloud` and `qwen3:1.7b`, muse's `muse-spark-1.3-contributor` and zai's `glm-4.5-air` all report 200,000 with `maxOutputTokens` 32,000, so for those wrappers "what the CLI reports" is the binary's default and not the endpoint's window (the table said 1,048,576 for muse and 128,000 for ollama). Only claude-code (1,000,000 for opus-5, opus-5-5 and sonnet-5; 200,000 for haiku-4-5) and zai's `[1m]` suffix are real per-model figures. Stored rows keep the window they were stamped with unless an operator explicitly repairs them with the bounded tool below. Historical measurements showed replay from retained `stream_log` could recover windows for the window is recoverable for claude-code 2,466 of 2,539 stored logs, ollama 206 of 213, zai 24 of 25, muse 6 of 6 and codex app-server 14 of 14 (12 of 3,429 logs are elided in the middle and all keep their `result` and token events, so only a peak there is a lower bound). These are historical sample counts, not a current inventory. `cliStreamLogRetentionDays` controls expiry: 0 means keep forever; a positive value expires logs after both invocation finalization and terminal task completion pass that age. On 2026-11-01 the owner changed this development install from 90 to 0 through the audited admin API; prompt retention was already 0. Future expiry is disabled under those settings, but already missing logs cannot be reconstructed.

## Repairing historical context badges (T402)

`packages/worker/scripts/backfill-context-usage.ts` is an explicit operator tool. It never runs at boot, calls a model, or initializes provider/catalog configuration. It changes only the three derived `task_steps.context_*` columns on completed steps. Billing, token totals, allowances, timestamps, raw transcripts and invocation records stay intact. Run from `packages/worker`, with `DATABASE_URL` supplied by the operator environment; the tool does not load `.env`.

```bash
pnpm exec tsx scripts/backfill-context-usage.ts --limit 25
pnpm exec tsx scripts/backfill-context-usage.ts --step-id <task_steps-row-UUID>
pnpm exec tsx scripts/backfill-context-usage.ts --limit 25 --after <nextAfter-UUID>
```

Default mode is read-only and inspects 25 done steps. `--limit` accepts 1–100, `--after` is an exclusive step UUID cursor, and `--task-id` / `--step-id` narrow the scope. There is no automatic pagination: inspect `hasMore` and use `nextAfter` explicitly. Counts describe only that batch, including changed, unchanged, missing and ambiguous cases. Reports and backups contain identifiers, derived values and evidence digests, never transcript/prompt bodies. Preserve them as operator metadata.

Replay shares the live Claude collector and Codex app-server request reader. A cumulative total cannot substitute for a request peak; Codex input already includes cache. A recognized legacy Codex exec stream can therefore clear an unsupported badge. Missing, malformed, mixed or elided evidence without an independently recorded modern peak is skipped; an elided peak is reported only as a lower bound. Unknown denominators, tied invocation selection and unavailable historical OpenRouter catalog denominators are refused rather than guessed. Existing modern request peaks can survive missing logs. Each invocation is capped at 8 MiB and each step at 64 eligible invocations; oversized, unended and unsupported data are disclosed. T403's wrapper/window-truth work remains separate.

Before applying, review a fresh inventory for the intended scope. Prepare an existing, durable operator-controlled artifact root **outside repository/sandbox-writable trees** and an existing child directory, and use a new relative backup filename per batch:

```bash
pnpm exec tsx scripts/backfill-context-usage.ts --limit 25 --apply \
  --artifact-root /protected/operator-root --backup context/run-001.json
pnpm exec tsx scripts/backfill-context-usage.ts --undo \
  --artifact-root /protected/operator-root --backup context/run-001.json
pnpm exec tsx scripts/backfill-context-usage.ts --undo --apply \
  --artifact-root /protected/operator-root --backup context/run-001.json
```

The first command inventories again and applies that fresh plan; it does not import the earlier dry-run output. The create-exclusive mode-0400 before-image and its parent directory are fsynced before any database mutation. Existing backup filenames are refused. Keep before-images separately; an administrator can still remove them. They contain database identity, completion/version fences, before/after values and an invocation-evidence digest. Successful rows commit together; NOWAIT conflicts are reported and skipped. Locks follow invocation → step order without a task-row lock. Reopened/completed-again steps, new/changed invocations and changed row versions win over repair.

Undo is read-only unless `--apply` is present. It uses only the backup's scope, checks database identity and the exact applied version/values/evidence, and refuses later changes. A backup includes planned rows that conflicted or never committed: undo reports those as conflicts, not as restored rows. Do not edit/reuse a backup. Exit 0 means successful inspection/mutation, 2 means explicit partial/conflicting apply or undo, and 1 means refusal/error. After an interrupted mutation inspect its backup and a dry-run undo before doing anything else: the database may have committed before the receipt appeared.

## Build stamps and dispatch

`haive_build` (`packages/worker/src/build-stamp.ts`, migration 0172) records which Haive build inserted a run, so runs before and after a prompt change can be compared by build rather than by timestamp. Four forms: `release:<HAIVE_VERSION>` on a published image (no `.git` above the worker and a non-dev version), `commit:<sha>` when the checkout's working tree equals HEAD's tree, `tree:<sha>` when it does not — the id of the tree the working copy would commit, so two identical states share it and any edit changes it — and `unknown` when none can be read, never a guess. NULL means not recorded: rows from before 0172, and a process that never ran `initBuildStamp`. The worker computes it ONCE at boot, before its first queue worker starts (about 0.6 s on this repository), and the three statements that insert a run stamp it (`insertOwnedRun`, step-runner's recap run and that run's failure record), so it names the build that INSERTED the row: a run requeued at boot executes on the next build. The dev watcher restarts the worker after a source change, which is what retakes it. The tree is built in a temporary index and object directory and writes nothing under `.git`. The index is seeded with `read-tree` of HEAD, the one call that sees the real objects (a C-quoted `GIT_ALTERNATE_OBJECT_DIRECTORIES`, since the variable splits on colons; a write through alternates would touch the real object files), so `add -A` keeps the committed mode wherever `core.fileMode` or `core.symlinks` says the disk cannot be trusted, as `git status` does, and a sparse checkout's skip-worktree entries keep HEAD's content (`write-tree --missing-ok`, since their blobs are only in the real store); tracked files an ignore rule matches are force-added. Replace refs are off for every call (`GIT_NO_REPLACE_OBJECTS`), so a commit id names its own tree, and `lfs.storage` points into the scratch directory, since the git-lfs clean filter would otherwise store a changed file's content under `.git/lfs`. Not covered: the gitignored `dist` of `@haive/shared` and `@haive/database`, and a linked worktree inside a container, whose gitfile names a host path, so it stamps `unknown`.

The dispatcher (`resolveDispatch`) filters to enabled providers, orders the resolved preferred provider first and the rest by the default priority (oldest `created_at`, `id` breaking a tie: `orderByDefaultPriority`, see [Step summaries](step-summaries.md)), and picks the first whose adapter is registered and has `supportsCliAuth` — plus `supportsSubagents` when the step declares the `subagents` capability. If none matches, the step is skipped. Every plan it emits is a CLI invocation; there is no API-mode branch. Auth mode selects which credentials the CLI is given, not whether the dispatcher bypasses the CLI.

`disableTools` is a best-effort optimization, never a provider eligibility requirement.
The Claude-family adapters and grok honor the flag; codex, gemini, amp and antigravity keep
their built-in tools available. The selected provider remains selected in either case.
`supportsDisableTools` still tells the dispatcher whether its prompt may truthfully state
that no built-in tools are available. Gate 3 and environment detection pair the preference
with `toolProfile:'none'`, which wires no MCP servers for every CLI. This preserves Muse's
deferred-tool compatibility fix without excluding CLIs that cannot disable built-in tools.
The former `requireDisabledTools` gate was removed after it routed a Codex task to a
quota-exhausted Claude provider and left the commit-message form empty.

Persona assignment is also recorded at DISPATCH in `cli_invocations.assigned_agent_ids`
(migration 0173), before a queued run starts or completion writes `tool_usage`. The terminal
header and split browser/terminal pane show one badge per assigned id. The run's `agentTitle`
stays separate: it can name a work item or pass (Validator / Fixer), which is not evidence of
a personality assignment. When that title repeats an assigned id (case, whitespace and
hyphen/underscore differences ignored), the header keeps the personality badge and hides the
redundant title. Legacy assignments are recovered only from recorded
`tool_usage.agents.assigned`, never from prompt prose, file paths or today's repository files.
Exec stamps the assignment again at start for jobs queued before this recording shipped.
The badge means ASSIGNED, not that the CLI spawned a native sub-agent or opened its definition.
Ordinary step prompts use inline protocols; eligible isolated calls paste the provider's
repository definition as described in [Per-call agent isolation](agent-isolation.md). Workflow
discovery miners carry their selected persona's title, description and field in the prompt.

The sub-agent emulator splits a single sub-agent specification into either a native `Task()` call (Claude Code) or a sequential prompt script (everything else). A sequential script runs inside a single `cli-exec-queue` job — the runner is an in-memory for-loop over the sub-steps, with no per-sub-step DB writes. A crash mid-script therefore fails the whole invocation; restart re-runs from sub-step 0. (Mid-script resume would require persisting each sub-step's parsed output to `cli_invocations` before moving on — not implemented.)

The Clean transcript's model segments keep their merged display text and first
`at`, plus optional `proseChunks` offsets and timestamps for each captured model
fragment. RAG usage review needs those timestamps to distinguish pre-query prose
from later actions within the same displayed segment. Timing metadata is capped
at 8,192 fragments per invocation; dropping old offsets leaves the display text
intact. Older transcripts lack this metadata and remain valid.
