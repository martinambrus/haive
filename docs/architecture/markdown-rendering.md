# Markdown rendering

EVERY prose body renders through `MarkdownView` / `.haive-md` (`packages/web/src/components/markdown/`). There is no plain-text branch. Underneath, the ONLY markdown renderer is `Markdown` (`components/markdown/markdown.ts`), react-markdown with `rehypeImageLinks` run last: an image in a body becomes a link to it and is never fetched, because every body is text an agent or a repository wrote and a fetch reaches the viewer's browser even inside a collapsed disclosure. `markdown.test.ts` fails on any other value import of react-markdown. Behind it, the page's Content-Security-Policy (`middleware.ts`, `lib/content-security-policy.ts`) admits images, media and fonts only from the page, `data:`, `blob:` and the api's host, resolved per request from the Host header because Next's `nextUrl` does not carry it, and named under both `http:` and `https:` because a TLS proxy hides the page's scheme from the server and Chrome does not let an `http:` source admit an `https:` URL on an explicit port; and mermaid (`mermaid-loader.ts`) draws labels as SVG text, locks its config against directives and frontmatter, and shows as code any source with a directive, frontmatter, `@{` shape metadata or a sequence `properties` line. PROSE is the word that scopes it: a form section carrying a structured payload instead of a body (`planImpact`, see [Plan canvas](plan-canvas.md)) is not prose and does not belong in a markdown renderer — but such a section leaves `body` empty rather than shipping the same content twice, so there is still exactly one rendering of anything. `looksLikeMarkdown` still exists but decides ONE thing — the LINE-BREAK POLICY, not the style: a markdown body gets `remarkGfm` alone so a model's ~80-col hard wraps reflow, a plain body also gets `remarkSoftBreaks` so its newlines survive as `<br>`. Do NOT re-promote it to a renderer switch. It used to be one, and identical prose then jumped between mono-12px `<pre>` and sans-14px `.haive-md` on nothing more specific than whether it happened to contain one backtick. `remark-soft-breaks.ts` is a deliberate local stand-in for `remark-breaks`, not an oversight: the dep is not in the pnpm store and adding one costs a full stack rebuild. An option LABEL is markdown too, but only where a rich element renders it (multi-select checkboxes, both radio variants) — the two native `<select>` renderers keep theirs plain because an `<option>` holds text and nothing else, so a label written for a dropdown must read correctly unrendered. That was already the de-facto contract: `02-plan-coverage` and `00-plan-sequence` write inline code into labels and it rendered as literal backticks. MEASURED across all 803 stored option labels before the change, 3 contained markdown syntax and 0 of them were on a `select`. A generator emitting a label must now escape or fence what it interpolates — `11f-plan-reconcile`'s `code()` sizes the fence to the content, since a node title carrying one backtick would otherwise end the span early and spill the rest of the label as markup. A body nested INSIDE another styled block (form/field/option descriptions, note fields) uses `InlineMarkdown`, which takes its size and colour from a WRAPPER element via `.haive-md-inherit` — putting those classes on MarkdownView's own element does not work, because `font-size: inherit` resolves against the parent, so a `text-xs` there would be what it inherits FROM rather than what it applies. Inline code under that modifier is sized as a RATIO of the body (`0.9285em` = 0.8125/0.875), never the absolute rem the plain rule uses, with `pre code` reset to `inherit` so the same selector does not scale it twice. `globals.css` is outside the repo's prettier glob (`ts,tsx,js,jsx,json,md`) and is hand-formatted compactly — running `prettier --write` on it produces ~150 lines of unrelated churn.
