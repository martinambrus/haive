# Plan canvas

`plan_nodes` and friends (`packages/database/src/schema/plan.ts`, migrations 0130/0131) are the durable, per-repo tree of what a project is MEANT to be — the intentional counterpart to the KB, which only describes how the code currently is. One plan per repo, enforced by a partial unique index on the root node rather than a `plans` table. A repo with no remote and no local tree is a first-class `source: 'blank'` repository: the repo-queue INIT job creates the storage dir, `git init`s it and lands one commit, so worktrees, task attachments and the `.haive-data/` mirror all work on a project that does not exist yet.

**One writer.** Every write — LLM turn, UI edit, markdown import — goes through `applyPlanPatch` in `@haive/shared/plan` (NOT the worker: the api writes plans too and cannot import the worker; `global-kb/task-context.ts` is the precedent for a shared package taking an injected `db`). It owns the materialised ancestry (`path`, self-inclusive and slash-terminated so one `LIKE 'prefix%'` selects a subtree), the `version` optimistic-concurrency check (a stale `expectedVersion` is a 409 the UI must SHOW, never a silent refetch), and subtree moves, which rewrite every descendant in one prefix-substitution UPDATE. Within one patch every op is checked against the version its node had when the patch first loaded it, so two ops a person approved together against version 3 both land; a version the node only reaches inside the patch, or a write by anyone else between two of its ops, is still a conflict. An agent's patch must carry that version for every existing node it changes or deletes (`requireExpectedVersion`, set by `applyAgentPatch`): an op without one is dropped and reported, where it used to skip the check and replace whatever a person had changed on the canvas since the agent read the plan. For the same reason it deletes only a node with no children, so a subtree goes leaf by leaf, each delete with its own version: the cascade from a parent would take descendants whose versions it never sent. An ordinal-only reorder is exempt, because the sequencing step writes a whole build order at once and a node-level version would reject it over an unrelated edit to one child (MEASURED: 1,350 of its upserts, none versioned); plan chat is shown every node's version (`withVersions`), which the committed mirror is not. The SQL offset must be cast — `substring(path from $n::int)` — because an untyped bind resolves to Postgres' POSIX-REGEX `substring(text, text)` overload and returns NULL. `importPlanMirror` is the ONE deliberate bypass: a mirror restore recreates nodes with their original ids verbatim (the spec writer and plan.md quote those ids), which the patch contract deliberately cannot express; it runs only when the repo has zero plan rows and refuses whole rather than half-import when the ids collide.

**Plan task types are not in `workflowTypeSchema`.** That zod enum is the create-task REQUEST validator; `plan_build` / `plan_chat` / `advisory` need a node id the generic form has no field for, so they are spawned by their own endpoints (`POST /repositories/:id/plan/...`) — the same arrangement `kb_author` already has. They live in the DB enum and in web's local `WorkflowType` union only.

**Completion greens the node** from the worker's `markTaskCompleted` (the only completion write; cancel and fail have their own functions, which is the point). Only `todo`/`in_progress` advance — `blocked_human` and `not_applicable` are verdicts a person entered, and a task finishing is weaker evidence than that. Status roll-up is DERIVED at read time (`rollUpStatus` in shared, one source for every view) and never stored: a `blocked_human` descendant makes every ancestor render blocked; green requires every descendant `done` or `not_applicable` — `not_applicable` must not prevent green, but must never render green itself either.

**Two triggers, one builder.** `createPlanBuildStep` (steps/plan/01-plan-build.ts) serves both the standalone `plan_build` task and the onboarding wrapper `10_8-plan-build` (index 14.5, after the KB and RAG exist, before the mirror is staged), because `onboarding_upgrade` reconciles template artifacts only and never re-runs onboarding steps — an already-onboarded repo can reach the builder no other way. The onboarding wrapper is opt-in (`askToRun`): its form warns of the token cost, defaults to skip and points to the Plan view's "Build from the knowledge base", the same builder later. The form keys on `askToRun` in the DETECT output, not on the option: the runner builds a form for any row with no saved schema, a `waiting_cli` one included, and reuses saved detect output, so a build in flight when the form shipped would otherwise park mid-build and drop its folded waves on the default skip. Only an explicit `buildPlan: 'skip'` declines (`planBuildDeclined`). The build is LEVEL-BY-LEVEL (wave 0 drafts root + level 1 via `selectAgents`; each later wave is thrown from apply() as a `MiningWaveError`, one agent per frontier node) because one pass cannot emit 400 nodes without truncating. Do NOT move it to `loop`: the runner's loop re-entry calls `resolveLlmPhase`, which asserts `stepDef.llm` exists — a mining-only loop step dies on its second pass with "reading 'prepare'" (measured, on a real repo). The frontier is recomputed from the DB every wave, and excludes `research`/`external` nodes (a blocker waiting on a person is not a system to decompose) and `taskable` leaves; per-wave agent ids (`plan-expand-<nodeId>-p<N>`) double as the asked-set, so a node is never re-asked even though apply passes are independent calls. Because a wave re-runs apply() with the CUMULATIVE result set and temp-ref creation is not idempotent, the fold is over `newAgentMiningResults` — `task_step_agent_minings.consumed_at` (migration 0132) is stamped on every row apply has folded right before the next wave dispatches and cleared on a re-roll, each row only at the run apply read (`consumeFoldedMiningRows`), so one another pass re-rolled meanwhile keeps its reply; for steps that never throw MiningWaveError the new field equals the cumulative set, so existing steps are unchanged. That set is decided once per pass, so each reply is also CLAIMED as it is folded (`applyAgentPatchOnce`, `_plan-prompt.ts`): its row's `consumed_at` is set, only while unset, in the same transaction as its patch, and so is the row's partial-apply note, since every later pass skips a claimed reply and a note written after the commit could be lost for good. Two apply passes over one wave, or one pass that re-runs apply in place after a wave that sent nothing, then write a reply once, and a reply another pass claimed counts as applied, so the builder's whole-wave re-roll does not fire on a wave that did land. 01, 02 and 03 all fold this way. A `ReopenStepFormError` consumes the rows apply folded and clears its detect output, form and answers in ONE transaction with `pause_form_on_retry` set, before it detects afresh, and writes the row only while the pass still owns it, since a Retry's reset keeps its own hold; a worker that dies before the new form is parked re-detects and stops at the form instead of re-sending the answered items with the old answers. The submit that led there can be redelivered, still carrying those answers, and a form submit carries no epoch to drop it by. While the hold is set, values a job carries are ignored, since the form has not been offered since. Once the form is parked, `isStaleSubmit` drops a submit older than the park. Every form park is stamped (`waiting_started_at`) in the write that parks it, not after, so there is no moment when a parked form has no park to be older than. A pass that dies between that write and marking the task waiting leaves the task `running`, and a stale submit landing on one parks the form again (`staleSubmitAction`) rather than only being dropped.

**Two modes, and the difference is the node status.** `from_repo` mines the KB and its nodes
arrive `done` because they describe code that exists; `greenfield` takes a written brief plus
any number of attachments and leaves them `todo`. A brief used to ride `from_repo`, which was
not inaccurate prompt copy but a project rendered as already finished. `from_md` (one inline
markdown document) is RETIRED from `planBuildRequestSchema` and deliberately alive in the
worker's `BuildMode`, so stored tasks stay retryable. An unrecognised stored value falls to
`from_repo` — a default rather than a throw, because that is what a revert would also produce.

**Clarifying questions come before the expansion** (`00b-plan-clarify`, index -0.5, opt-in per
task through `tasks.metadata.planClarify`, which the build route sets by default for a brief and
only on request for a knowledge-base build). The planner drafts root + level 1 from what the inputs
state, every assumption and conflict an open `decision`/`research` node directly under the root; a
questioner asks about it; the planner folds each round's answers in as a patch and marks every
answer `settled` or `open`, and open ones are asked again. The owner ends it, and 01 expands the
outline (its depth form says so through `outlineFromThisTask`). Planner and questioner are mining
SEATS (`STEP_MINING_SEATS`), not loop roles, so each runs on its own CLI. An answer the owner TYPED
reaches the planner as operator text; a suggestion they clicked was written by the questioner and
stays fenced (`ClarifyAnswer.suggested`), since a repository it read could have steered it; the route seeds the
questioner as a task step choice. Three decisions to keep. It cycles like 02, by waves and
`ReopenStepFormError`, NOT plan chat's self-revise: that reset deletes every round's agent rows and
supersedes their invocations, dropping the spend from statistics. Rounds live in
`plan_clarify_rounds`, and every move (`nextMove`) is decided from that table and the plan root, so
a Retry, a reopen and a redelivered submit all land on the same step; answers are written only
while `answered_at` is null, and a field id carries its round, so a stale submit for an earlier
round reopens the form instead. The route refuses a repository that already has a plan, but only
when the task is created, and a deferred build waits while its files upload; so the outline fold
also writes a round 0 naming the root it drafted (`root_id`, nulled if that root is deleted), and
the step refuses any other root (`assertOwnOutline`): one written before it started, or one someone
recreated while a round was parked. The api also refuses to delete the root, or to create one, while a clarifying build is open
(`refuseRootChangeDuringClarify`): through the questions AND through 01's depth form, since a root
rebuilt there by 01 alone would carry none of the answers; cancel the build to change it. A plan
chat is refused then too: its agent patches the whole plan and would race the answers being folded in. Behind
that, a deleted root with no replacement is simply redrafted, under a numbered agent id
(`clarify-outline-N`), since a step never re-sends an id it already has a row for. A
node's `sourceTaskId` cannot serve, since every later patch, a canvas edit included, rewrites it. Answer folds also drop an op that deletes the root or adds another, which would leave round 0 naming
none. 01 and 02 treat the WHOLE outline as this build's when round 0 names the current root
(`ownsClarifiedOutline`), since a canvas edit during the questions clears a node's `sourceTaskId` and
would otherwise take a `done` from_repo branch off the frontier. Its folds drop any node placed below the root
(`outsideOutline`): 01's frontier expands component LEAVES only, so a decision put under a
component would take that component out of the build with nothing reporting it.

**plan_chat** is one conversation on one card: a self-targeting `reviseLoop` re-parks the form every turn and the user ends it by submitting nothing. The transcript lives in `plan_node_messages` precisely because that revise resets the step row each cycle. The prompt carries the newest whole turns within 24,000 characters and a count of the earlier ones (`recentTurns`, `plan/transcript.ts`, shared with the plan merge), always the newest, which is the message being answered. The agent is handed the WHOLE plan (via `renderPlanMarkdown`, the same render committed as `.haive-data/plan.md` — one function so what the agent reads and what is committed cannot drift), so a request made while looking at one node can correctly patch another. **advisory** researches a non-code blocker and then STOPS: `02-advisory-decision` parks on a form and only the USER closes it — an agent concluding an unsigned contract is fine would turn a real blocker into a green tick.

**A sibling run too wide for one agent's reply is named, never sent.** The build-order step
(`03-plan-sequence`) asks one agent per undecided run for an upsert per child plus the links it
adds, and a patch holds `PLAN_PATCH_MAX_OPS` (500) ops, so a run past `SEQUENCE_MAX_RUN_CHILDREN`
(half of that) keeps its stored order and the finished step names it (`degradedNote`), and the
prompt states the op budget its reply has. `tooWideToSequence` is the one rule the fan-out and the
plan page's Order count (`computeSequenceProgress`) share, so the count never promises a pass that
would skip a group. A group counts as asked (`askedParents`) only while its agent row is `done`: a
reply rejected at apply (no patch, or one the applier refused) sets the row `failed`, so the next
pass asks that group again and the Order count keeps it. Each agent sees its node's neighbourhood, never the whole plan:
`buildPlanExpansionContext`, the helper 01 and 02 use, with the build-order number `#N` on every line
and no dependency information, and the context and the child list share one bound,
`SEQUENCE_CONTEXT_BUDGET` (96,000, as `PLAN_EXPANSION_CONTEXT_MAX_CHARS`). A child list at the cap
stays under it since `safeTitle` caps a title at 200 characters (MEASURED: no stored run came near the
cap, widest 33), and the helper keeps its own cap on a deep ancestor chain by dropping the most distant
ancestors behind one line that counts them. MEASURED on committed plan snapshots: the prompt p50 went
from 148,443 to 106,629 characters on a 7,983-node plan (870 agents) and from 119,003 to 106,622 on a
4,106-node one, while a 1,044-node plan grew slightly (103,099 to 106,909) as the sampled outline fills
the budget. Of the 9,312 `depends_on` ops sequence agents ever wrote, 9,288 joined two nodes of the
agent's own section and 24 were malformed, so the bounded view cuts no link an agent made.

**"Start next" is STRICTER than the gate that refuses a task, deliberately.** `computePlanReady`
(`shared/plan/ready.ts`) picks the lowest-numbered node that is startable now: `todo`, no unmet
`depends_on` of its own, **no ANCESTOR with one**, no open task on it, and a unit of work
(`taskable` for components and developer-task decisions; a leaf for human decisions,
research and external work, which carry `taskable` only sometimes — MEASURED 10 of 16 research
and 4 of 12 external nodes). A non-taskable leaf decision is still something a person can
resolve: MEASURED on the 20-node elmont_novy plan, the four foundation tasks and hosting were
done, but the unanswered domain decision was not taskable, leaving the ready set empty while
both catalogue and revisions waited on it. Such decisions now appear as **Decide next**, which
opens their panel to record the answer and mark Done; `taskable` decisions still open the
new-task form. `nextUp.node.taskable` tells the browser which action to offer. The ancestor
half is the point, and it is the half `blockedById` deliberately omits: MEASURED, 1,286 of
7,079 taskable nodes in one plan carry no prerequisite of their own and 23 also have a clean
ancestor chain, and on another plan the
lowest-numbered node the DIRECT rule calls ready (#28) sits under two containers that are
themselves waiting, while the strict rule picks #65. Do NOT reconcile the two readings: a rule
strict enough to CHOOSE must not REFUSE, because choosing badly wastes a click while refusing
badly turns one wrong-direction edge (15 of 16 unsatisfiable deps were exactly that) into a
locked subtree. `POST /tasks` stays direct-only; the node panel's `ancestorBlockers` banner is
what explains the skip, and says out loud that it does not stop you. Cycles need no test of
their own — their members never lose their blockers, so rules 2 and 3 already exclude them and
everything beneath them. `nextUp` rides the plan overview (a property of the PLAN, like
`ordering` and `defects`); the SET behind the count is `GET /plan/ready`, served in the exact
shape `/plan/search` returns so the page filters it with the machinery it already has, capped
at 200 and REPORTING the cap.

**Human resolutions have a direct form.** A non-taskable decision is labelled **Needs your
decision**, and an external item **Needs action outside Haive**, with **Record decision** /
**Record outcome** actions. Neither offers a developer task or the grid's task checkbox;
taskable decisions still do. Decision kind badges are visible even though the creation picker
does not offer that kind. The form uses `FormSchema` / `FormRenderer`, shows the existing
question, requires an answer, and offers **Resolved**, **Still waiting**, and **Not applicable**.
Unresolved items default to Still waiting so recording partial progress does not green them.
An item's own `done` or `not_applicable` status changes the panel to **Human item settled**,
with guidance for reopening it instead of instructions to act. Resolution and advisory buttons
are hidden until its status is reopened; Still waiting keeps both available. The description
and recorded answers remain visible. A successful write that reloads a settled status also
closes an open resolution form, including when the status editor settled the item.
The endpoint `POST /plan/nodes/:nodeId/resolution` checks repository ownership and the item's
kind, then passes one versioned body-and-status upsert through `applyPlanPatch`. The question
and prior answers remain verbatim, with a new `## Decision` / `## Outcome` section appended;
an unclosed top-level fence is closed through `scanFences` before that section. The form holds
the question and version it opened on, so a concurrent edit returns 409 and keeps the draft.
No migration or CLI invocation is needed to record an answer. **Help me evaluate the options**
is a separate optional advisory run; research still ends at a human decision gate. The pure
`@haive/shared/plan-resolution` subpath holds the shared UI/API policy and form without pulling
the database or host filesystem into the browser.

**An advisory holds its question.** Open advisories are linked by `tasks.metadata.planNodeId`,
not by `plan_node_tasks`: they neither implement a node nor touch its code. Readiness includes
those metadata links in its open-task exclusion. The node detail names an open advisory so
the panel offers **Continue research**. Advisory starts lock the plan node, reuse an existing
open advisory, or insert the new task in that transaction through `spawnPlanTask`'s injected
writer, which claims its START (`markQueuedForStart`) in the same transaction; `enqueueStart`
queues it only after commit, and a reused advisory is re-driven by `enqueuePlanTask`. Two tabs
therefore continue one run. The advisory's final form writes with its detect-time node version,
matching the question and body it actually showed: a direct answer or plan chat landing while
it is parked must conflict rather than be overwritten with stale text or status. A freshly read
version with a detect-time body used to bypass that protection.

**Impact answers "if I change this, what else must change?"** (`shared/plan/impact.ts`): an explicit BFS with a visited set, because the edge graph has cycles by construction and a recursive CTE without dedup would not terminate while one with dedup could not say where it stopped. Both caps are REPORTED, never applied silently. The mermaid source encodes nodes as a `pnode<32 hex>` token; the browser recovers the uuid from THAT, unanchored — mermaid prefixes rendered ids with its own render id, so a `^flowchart-` anchor binds zero handlers and fails silently.

The walk takes a SET of origins, because gate 1 asks the question of every component a spec named rather than of one of them. Two consequences. `depth` is then the distance to the NEAREST origin, which is the honest number — the per-origin walks it replaced recorded whichever origin reached a node first in list order, and MEASURED on a real task that reported 1 node at one hop where the multi-origin walk finds 72. And every origin is seeded as visited, so the walk never discovers an edge BETWEEN two origins: `renderImpactMermaid`'s `edges` option exists to draw those, and without it a multi-origin picture is a row of disconnected boxes. The diagram's `maxNodes` bounds HOPS only — origins are always drawn, so a caller with more origins than a picture can hold must decide not to draw one. **Code links** have one writer (the applier; the builder only links files it actually opened, with `evidence`) and rot is flagged, not guessed away: `11c-rag-reindex` marks links stale for the paths in `tasks.changedPaths`, and only re-assertion by an agent clears the flag — the difference between an impact view that is wrong and one that is merely old.

**Spec-writer integration:** when the repo has a plan, 04-phase-0b is handed a compact component index and must emit an `## Affected components` section naming `node:<uuid>` ids. `resolveAffectedComponents` (`workflow/_affected-components.ts`) parses those IDS — never the agent's prose, because name-matching picks the wrong node the first time two read alike — and walks the edge graph from all of them. It lives in its own module because two steps must agree on the answer: 04 stores it for the implementer's prompt (`_plan-impact.ts`, which states the invariant — agent and human reading different blast radii is worse than either reading none) and 06 renders it to the approver.

**Two things bound what the plan can do to that prompt, and both were measured on a 544-node plan.**

`recordTouchedPlanNodes` writes a `touched` link for every component the spec named, and `loadSeededPlanNodes` reads `implements` ONLY. Reading both made the step feed its own output back in: MEASURED on task 681f0f99, 5 links at task creation, +157 the moment 04 round 0 ended and +201 the moment round 1 ended, so 363 nodes were re-rendered IN FULL WITH BODIES — the seeded block went 9,493 to 232,365 chars and the whole spec prompt 219,412 to 441,506, against 43,641 for the same task with no plan. It compounds every round. That is the same role split `completePlanNodesForTask` relies on to avoid greening a node the task merely touched, so a reader that ignores the role is the bug, not the column.

`renderBoundedPlanIndex` then steps the index's DEPTH down until it fits `PLAN_INDEX_MAX_CHARS`, stating the reduction in the prompt. Depth, not a character slice: a slice ends mid-node and leaves a truncated `node:<uuid>` the writer can quote back as whole. The bound is a GUARD RAIL — 120k sits above every index measured on a run that went well, so nothing observed working is trimmed. Worth knowing before tuning it: the index is the DOMINANT term in every planned run, MEASURED at 93,035 of 124,215 chars (75%) for a 174-node plan, 115,620 of 133,331 (87%) for 193 nodes and 158,274 of 219,412 (72%) for 544. Whether a shallower index costs spec quality has NOT been measured; ~40k halves the spec prompt and is the experiment to run.

**The gate renders it as the plan canvas's own Impact view, not as prose.** The section carries `planImpact` on the form schema (`shared/schemas/form.ts`) and `PlanImpactSection` (`web/components/plan/`) draws depth groups → relation sub-groups → click-through rows, reusing the `PlanImpactList` the detail panel's Impact tab uses. It replaced one markdown list: MEASURED on a real task, 363 flat bullets in a `max-h-96` scroller holding 10,459px, with the distance an impact answer is ABOUT reduced to a `(2 hops)` suffix, nothing clickable, and a diagram seeded from `named[0]` ALONE that drew 19 of the 363 while reporting `mermaidOmitted: 0`. `body` is empty on such a section — one rendering, not two — and a section persisted before `planImpact` existed has neither and still renders as markdown, which matters because `task_steps.form_schema` is STORED and only rebuilt when it is null. 06's detect re-walks a payload that predates `mermaidDepth` rather than defaulting `reversed`, since a fabricated direction inverts every "Depends on" / "Depended on by" heading.

**The radius is a control, not a constant.** The gate carries the same reach buttons the Impact tab has, but over a FROZEN snapshot — so the resolver renders one bounded diagram per radius the walk reached and the buttons switch between them. The browser cannot draw its own: a hop in the payload carries no `viaNodeId`, and re-deriving a traversal there would put the cycle guard and the caps in two places. Only radii the walk actually reached get a button, because the panel's fixed 1-4 can afford one that returns nothing (it re-fetches) and a snapshot cannot.

`IMPACT_DIAGRAM_MAX_NODES` is the whole picture's budget, spent on ORIGINS first and on neighbours with what is left, so a wide named set draws origins alone. That is a real subgraph, not a row of loose boxes: MEASURED on the 161-named task, the first 40 named components carry 40 edges between them and only 4 of the 40 are isolated (217 edges among all 161) — which is why an earlier version that refused to draw past 40 origins was wrong. Origins are taken in SPEC order because which 40 got drawn has to be answerable, and "the ones the spec cites first" is checkable where a connectivity ranking is not. `namedOmitted` states the rest. A consequence worth knowing: nearest-first ordering means a wider radius only appends nodes that the budget then cuts, so once the picture is full it stops changing with the radius while the list keeps growing — the omission line says so. No count is ever subtracted from another: the diagram and the list walk different radii from different origin sets, so no arithmetic between them would be true.

**A conflicted pull is resolved as a conversation** (`plan_merge`, `01-plan-merge`). Save and Pull merge the remote into one scratch worktree per repository (`.haive/worktrees/plan-merge`, detached at the checkout's HEAD) and only ever fast-forward the branch onto the result; what conflicts outside the two mirror files goes to a task. A conflicted `.haive-data/plan.json` is merged three-way inside the merge itself (`resolveHaiveProjectionConflicts`, `worker/src/plan/projection-merge.ts`): `mergePlanMirror` over the merge base, ours and theirs (a missing base is no base), so the merge commit carries both installs' changes. A field both sides changed differently takes THEIRS in the file, as the flush does for a pending question, and the reconcile afterwards asks it. `plan.md` is rendered from the merged plan.json (`renderPlanMarkdownFromMirror`, the same bytes the flush writes), and the bytes go in through `hash-object`, `update-index` and `checkout-index`, never a path write. A side that does not parse, plan.json files with different roots, or a merge that fails fall back to the incoming side for that path with a warning (`PlanMergeAttempt.warnings`, logged); where one side deleted plan.json and the other kept it, the kept side stays, since dropping a plan is not a merge. A conflict anywhere under `.haive-data/state/` merges the whole project state record the same way: `mergeProjectState` over the merge base, ours and theirs, read from the trees, with a unit both sides changed taking THEIRS in the file (the post-merge sync asks it) and the result re-rendered by `renderProjectState` and staged through the same index calls; a file the merged record no longer holds is removed with `git rm -f`. A side that does not parse or a merge that fails takes the incoming side of every path still unmerged under the directory, with a warning, so none is ever left to the agent. The agent's working directory IS that worktree (`llm.worktreeRel`, carried on both the dispatch and the job), so the prompt names paths relative to it and a stray file lands in the merge, where the relocation sees it, never in the person's checkout. Asking for a change after the merge was resolved reopens it (`reopenResolvedMerge`): the worktree goes back to the merge's first parent and the remote is merged again, so the agent resolves the conflicts as git opens them, under the new guidance. That happens only while the worktree's HEAD is a merge commit that has not landed on the branch. Nothing of the previous answer is copied back into the files: a per-path copy could not restore what git records, a deletion, a mode or a directory/file choice, and silently reversed them. It is carried as reference text instead, so a choice the person did not restate is not rebuilt blind. Before the reset, detect records a `plan_merge.prior_resolution` task event (`sha` of the merge commit and `head`, its first parent) beside the transcript, since the revise loop resets the step row and the reopen resets the worktree; a crash between the record and the reset writes it once, and one between the reset and the merge still finds it. While the worktree stands on that `head`, the prompt renders the transcript (the agent's turns fenced as plan chat does, the person's not; the newest whole turns within 12,000 characters, with a count of those left out, through the same `recentTurns`) and, for each conflicted path, what the commit holds there, read with `ls-tree` and `cat-file` and never from the files (`merge-prior.ts`): the content fenced and cut at 6,000 characters per file, 30,000 in all and 40 paths, or that the path was deleted, was a directory, or sat under a file, and a path git moved out of a directory's way (`docs~HEAD`) also names the shape the answer gave the path it was moved from. A commit that can no longer be read is stated as unavailable and the pass goes on. It is labelled reference only: git's current conflict state is what is resolved, and the person's new guidance wins. The conversation is one task, which a confirm or a discard ends, so the newest record is the round, and a record whose `head` is not the worktree's HEAD is not shown. A cancel discards the worktree (`discardPlanMerge`) unless another `plan_merge` task of the repository may hold it: a live one, or a failed one opened after the cancelled one, whose Retry resumes the merge. Opening a conversation (the api's `POST /plan/merge`), a Save or Pull's use of the worktree (`integrateOrigin`, which also refuses once a live conversation exists) and that discard each run under one repository-scoped lock (`lockPlanMerge`, `plan-merge:<repositoryId>`), so none of them can lose the worktree to another half way. Reviving a `plan_merge` task (any Retry, Resume or auto-resume) takes the same lock first (`reviveRefusal`), since a revived conversation takes the worktree back. A FAILED conversation keeps its worktree, because a Retry resumes it, and Save or Pull may still discard it. Conflicted names are judged on their bytes (`conflictedPaths`): a valid name holding U+FFFD is listed, one that is not UTF-8 is only counted.

The mirror (`worker/src/plan/mirror.ts`) writes `.haive-data/plan.json` + `plan.md` from every plan-step apply and from `12-post-onboarding`; `persistDetection` imports it on clone. Both files are canonical, so the same plan writes the same bytes on every install. `serializePlanMirror` orders the nodes in tree pre-order (siblings by ordinal, then id), the edges by from, to and kind, and the code links by node, path, symbol and role, and plan.md lists a node's links in that edge order. The rows' read order is not: a seq scan and an index scan on `plan_nodes_repo_parent_ordinal_idx` return a root and its first child, both ordinal 0, in opposite orders, and a second install's Save once committed that reorder.

**A move of the checkout Haive drives (00a's fast-forward, refresh, a plan Pull, Save & push and the `01-plan-merge` confirm) sets a dirty `plan.json` and `plan.md` aside first.** `plan.json` must hash to `synced_hash` and the database must hold a plan, else the move is refused naming it; `plan.md` is never judged. The mirror's revision is bumped before the files return to HEAD, and the re-sync after the move reconciles the new head's plan.json against `synced_snapshot` and flushes (`setAsideHaiveProjections`, `resyncHaiveProjections`; [Onboarding template versioning](onboarding-upgrades.md)).

**A flush writes only over bytes Haive has read, and reads the rest in.** `plan_mirror_state.synced_hash` (migration 0195) is the sha256 of the raw bytes of the `plan.json` Haive last wrote or last read in, or the sentinel `absent`: `writePlanMirror` stamps it after every write (a removal stamps `absent`, which no sha256 equals, so a plan.json that arrives later counts as unread; an empty plan.json never counts as synced, since Haive never writes one and rows stamped before the sentinel hold the empty string's hash), `importPlanMirror` and `reconcilePlanFromCheckout` stamp the bytes they read (hashed as bytes, never as decoded text, and only if, just before the commit, plan.json still holds them and no merge or rebase has opened), and `stampPlanMirrorHashesAtBoot` stamps clean unstamped rows whose file already equals the render. `writePlanMirrorLocked` throws `PlanMirrorHeldError` with nothing written and the row left dirty while a merge or rebase is open — `MERGE_HEAD`, `REBASE_HEAD`, `rebase-merge` or `rebase-apply` exists in the git dir (`gitOperationInProgress`, `repo/git-operation.ts`, shared with the project-state sweep; a git that cannot say fails the flush instead, see the failed-read rule below). When plan.json exists and its hash is neither `synced_hash` nor the hash of the render about to be written (a pull git did without Haive, or a hand edit), the flush reconciles it into the database first, under the lock it already holds, then renders again and writes (with no base and unwritten edits of its own it holds instead: nothing says which side is newer, and Pull is the explicit way to take the file); a file that cannot be read in as a plan (not JSON, not a plan, parentage that does not close, a different root) holds the flush with that reason instead. plan.json is replaced or removed only through a parked operation (`writePlanJsonIfUnchanged`, `removePlanJsonIfUnchanged`) that re-checks for an open merge and replaces only the exact bytes the flush judged, so bytes a pull lands meanwhile are kept and the flush holds. plan.json is written before plan.md, and a failed plan.md is thrown only after the stamp commits. Every read of plan.json stops at 16 MiB (`PLAN_JSON_MAX_BYTES`): a larger file is held or refused unread, and a render past it is never written. A row with no `synced_hash` (written before 0195 and not matching at boot) adopts the file as it always did, with a logged warning, rather than holding forever. Every step caller of `writePlanMirror` already catches and logs, and Save fails with the reason, so a held plan never fails a step. The sweep takes the 25 oldest dirty rows by `updated_at` and touches a row that failed or was held, so stuck rows cannot starve the rest.

**The three-way reconcile.** `reconcilePlanFromCheckout` (`worker/src/plan/mirror.ts`; Pull, Save after an integration, the `01-plan-merge` confirm, `persistDetection` when plan rows already exist and the row was stamped, and the flush above) takes the plan-mirror lock, reads plan.json, returns at once when its hash is `synced_hash`, and otherwise runs the pure `mergePlanMirror` (`@haive/shared/plan-mirror-merge`) over base, local and incoming. **Base** is `plan_mirror_state.synced_snapshot` (migration 0196): the checkout's plan.json as it was when Haive last read it in (`importPlanMirror` and every reconcile store it), NOT the merged result. A merged result would carry local-only nodes and local edits into the base, and the next pull would then read "in the base, missing from incoming" as a deletion by the other side, or an unpushed local value as agreed. Readers that want a row's counters select columns (`plan-mirror-queue`, `/plan/snapshot`), because the snapshot is the whole plan. **Local** is the database rendered exactly as the flush writes it (`renderPlanMirror`). **Incoming** is the file; a schema-v1 file cannot carry code links, so it keeps local's. With no base (a plan this install authored, or a row from before 0196) the merge only adds and incoming wins, as a reconcile did before it had one; the first read of a checkout stores the base. The merged result is applied to the database creating nodes with their own ids, and a node's `version` and `updated_at` move only when one of its fields actually changed (an unchanged node keeps the version an open editor holds, so a Pull that brings nothing new produces no 409); a status change stamps or clears `done_at`, and a changed node loses its plan-build `source_task_id`, the way `applyPlanPatch` does for a canvas edit. Delete wins only over a node nobody here touched: a local modification, or something modified under it, keeps the node and its ancestors. A title, body, kind, status or taskable both sides changed differently keeps the database's value and becomes a pending `project_state_conflicts` row, `plan/<nodeId>#<field>` with `{ v }` base, local and incoming sides; ordinal, parent, edge and code-link differences keep local and are reported (`PlanPullOutcome.conflicts` lists the questions, `nodesDeleted` the deletions). While a row is pending the flush writes the INCOMING value of that field into plan.json (the other side's file is not overwritten with this install's value before anyone chose) and renders plan.md from the database; the next reconcile re-asks until the two agree, closing a row whose field no longer conflicts or whose node is gone as `converged`, and deleting the plan closes the rows and clears the snapshot. Plan units are conflict units of the project state record (`isConflictUnit`; `isPlanUnit` names them), so the api lists them with the node's current title (`nodeTitle`, null once the node is gone) and the plan page answers them through the same banner; `blocksUpgrade` stays false, so a plan question never holds an upgrade or an admission, and the onboarding reset spares them, since it takes back files and the plan is not one. An answer (`answerPlanQuestion`, `worker/src/plan/answer.ts`, from `answerInTransaction`) takes the plan-mirror lock after the plan-merge and project-state locks and before any repository, conflict or node row is locked (a reconcile holds it while it writes all three, so a row lock taken first would deadlock against it), then locks the node row; a live onboarding does not hold it, since nothing here writes a checkout file but the flush. A node that is gone, or whose field already holds the incoming value, closes the row `converged`; a field edited since the question was asked (no longer the row's `local`) refreshes `local` and answers `moved`. Take theirs writes the incoming value into the node (`version` and `updated_at` move, a status change stamps or clears `done_at`), keep mine leaves it; both set that field of the base to the incoming value (a node the base does not hold stays out of it), close the row and mark the mirror dirty, and the worker flushes right after the commit. The next reconcile of the file then finds base, file and database agreeing (take theirs) or reads this side's value as a local change since base (keep mine), and asks nothing. A snapshot stored as the base keeps each contested field at its previous base value so the question survives an unrelated pull. A Save or plan-merge confirm that pushes also moves the base to what it pushed, read from the commit taken before `pushBranch` (`advancePlanBaseFromCommit`) once that commit is in the remote branch and the branch tip still carries the same plan.json (a slower Save never moves the base back over a later push), so the other side's next change is not mistaken for a conflict with this install's own pushed value; a field still asked about keeps its old base. A question settled by a local edit to the incoming value moves that field of the base too, and one whose node is gone closes. A plan.json whose root differs from this plan's shares no history and is refused before merging, so it can never read as "every node deleted by the other side". Every node update, delete and path repair is fenced on the `version` read before the render, so a canvas edit committed during a reconcile holds it rather than being overwritten, and a deleted node with a child outside the deletion holds instead of taking that child by cascade.

**A failed git read is unknown, never a definite answer, and only an exit code says otherwise.** `divergence` (`worker/src/plan/merge.ts`, behind Save, Pull and the `01-plan-merge` step) reads a missing `origin/<branch>` as nothing to pull and throws on every other non-zero exit or unparsable count: `rev-parse --verify --quiet origin/<branch>^{commit}` exits 1 for the missing ref and 128 for a failure, `merge-base` exits 1 for no common ancestor and 128 for a failure. It used to count a failed `rev-list` as 0 and any failed `merge-base` as unrelated histories, so a Pull whose git had failed reported success having pulled nothing. `branch --show-current` is read by `currentBranch` in `plan-mirror-queue.ts` (Save and Pull) and in `01-plan-merge.ts` (detect and the cancel path): a non-zero exit throws `git branch failed in <dir>`, and only exit 0 with empty output is a detached HEAD. `GET /plan/snapshot` reports `gitAvailable`, `tracked`, `uncommitted` and `hasOrigin` as `null` when their read failed: `ls-files --error-unmatch` exiting 1 is the only "untracked", `remote get-url origin` exiting 2 the only "no origin", and a failed `rev-parse --is-inside-work-tree` makes the others null without reading them (exit 128 is every fatal failure, so a directory that is not a repository reads as unknown too). `committed` needs `tracked` true and `uncommitted` false. Every exit code named here was MEASURED on git 2.43.0 and on 2.54.0, the version both images ship, and the two agree. `branch` stays `string | null`: null is a detached HEAD or an unread branch, which cannot be told apart without a new field. The plan page renders null neutrally (`snapshotStatus` and `showsPushAndPull`, `web/src/lib/plan-snapshot.ts`): "Commit state unknown" in a neutral colour, never "Not committed", which needs `tracked` false or `uncommitted` true; Save & push and Pull stay offered, and "Link to origin", which says there is no origin, appears only when git said so (`hasOrigin` false) or while the snapshot loads.

**The same rule covers the origin reads, the worktree lists and the HEAD reads that feed a move.** `getOriginUrl` and `detectOrigin` (`worker/src/repo/git-push.ts`) share one `git remote get-url origin` read: exit 0 is the URL (the remote's name when only a fetch refspec or push URL is set), exit 2 the only "no origin", and any other result (128 for a broken `remote.origin.*` value or a directory that is not a repository, the 124 of a timeout, the -1 of a run with no exit status) throws `git remote get-url origin failed in <cwd>: <output>`. The old `git remote` read gave the same exit codes and turned every failure into "no origin"; MEASURED on git 2.43.0 and on 2.54.0, and a bad `remote.origin.fetch` fails this read alone, since rev-parse, status, branch and symbolic-ref still exit 0 after it. Plan Save and Pull, `00a-sync-base`, `11a-gate-4-push`, `12-worktree-cleanup` and `13-onboarding-push` let the throw fail the step with git's text, and a Retry reads again. `12-post-onboarding` and `99-run-app-ready` say in a comment that they must not fail (the first writes its artifact rows and the mirror in apply, the second keeps the runtime serving), so they record an optional `originError`, show one warning note and withhold the push fields. `repo/refresh.ts` answers `Not refreshed: could not read the remote (...)` beside a ready repository; a throw would set the repository to status `error` (`queues/repo-queue.ts`) and take its Terminal, Create task and Plan away. `isWorktreeRegistered` (`repo/git-workspace.ts`) is the one reader of `git worktree list --porcelain` for the plan scratch worktree, the cross-branch base worktree, a DAG issue worktree and `01-worktree-setup`: a non-zero exit throws `git worktree list failed in <repo>`, because read as "not registered" it sent the caller to remove a worktree that is (MEASURED: the setup step deleted the task's feature worktree and an uncommitted file in it, `worktree add` then refused the path as "missing but already registered", and the next Retry wedged on "workspace does not exist" until a `git worktree prune`), and `worktree-list-guard.test.ts` fails a second copy. For the merge itself, exit 1 of `rev-parse -q --verify` is the only "no merge open" or "no such ref" (`commitMerge`, `mergeIsOpen`, and the merge dir's `revParse` in `step-engine/git-merge.ts` that merge-baseline shares, see [Merge conflicts](merge-conflicts.md)): a failed MERGE_HEAD read used to skip the merge commit, so `landPlanMerge` fast-forwarded onto its own HEAD (exit 0) and a Pull reported success having pulled nothing. Save and Pull's work-tree probe throws `git rev-parse failed in <repo>` unless git itself answers `false`, and `headCommit` (`plan/merge.ts`) throws on a failed `rev-parse HEAD` wherever the read becomes `before` for `recoverAfterMoveFailure` (Save, Pull, `integrateOrigin`, the `01-plan-merge` confirm, `landPlanMerge` and `00a-sync-base`; `refresh.ts` returns `Not refreshed: the checkout's HEAD could not be read (...)` instead): an empty `before` made every unmoved HEAD look like a landed move and took the re-sync branch instead of putting Haive's set-aside files back. Each of those reads happens before anything is set aside or moved (`00a-sync-base` reads it ahead of its set-aside for that reason), so a throw leaves nothing to undo. The read after the move stays nullable, since the checkout has moved by then, and `fastForwarded` comes from `integrated.landed` instead of comparing two reads. `recoverAfterMoveFailure` (`project-state/set-aside.ts`), which runs when a move throws, reads HEAD again to learn whether the move landed: it puts the set-aside bytes back only when HEAD is still `before`, and a HEAD that moved or cannot be read takes the re-sync branch instead (`resyncHaiveProjections`, `restoreKeptMetadata`, and a warning when the read failed) and rethrows the original error. MEASURED: a put-back after a landed move writes the stale pending bytes over the incoming `plan.json` (and deletes an incoming file that was pending deletion), after which the next flush reverts the other install's plan edits; the re-sync cannot lose content, since the sync base was rebased onto HEAD's record when the files were set aside, and costs only the staged index entry of a projection a person had staged. A plain `rev-parse HEAD` exits 128 for an unborn HEAD as well as for a failure, so a repository with no commit takes that branch too. `GET /plan/snapshot` takes the repository root from the row `requireOwnedRepo` loaded (`storagePath ?? localPath`; both are null while a repository clones, which is a real "no checkout") rather than from a second query whose failure read as one. `gitOperationInProgress` (`repo/git-operation.ts`, behind the plan flush, the project-state sweeps and the set-aside gates) asks `rev-parse --git-path` for each state entry, which exits 0 for every entry whether it exists or not and 128 for a corrupt `.git/config` or no repository (MEASURED on git 2.43.0 and 2.54.0, which agree). It used to skip a failed read as "no such entry", so a flush or a move went on into a tree with a merge or rebase open (MEASURED: `merge --ff-only` is refused over an open merge but succeeds during a rebase stopped at `edit`, so for a rebase this guard is the only protection). A checkout with no `.git` (an uploaded archive or an in-place folder, a supported checkout) has no operation whatever git answers there (`gitWorkspaceStatus` `absent`), and its plan files are still written. In a checkout that has one, a read that fails (128, the 124 of a timeout, the -1 of a run with no exit status), a `.git` that is a link and a state entry that cannot be read throw `GitOperationUnreadableError` (`git rev-parse --git-path <ref> failed in <repo>: ...`). The plan flush and the project-state sweeps let it fail the row: nothing is written, the row stays dirty, `last_error` carries git's text (not "a merge or rebase is open", which the plan page would show), and the sweep goes on to the next row. The three set-aside gates (`restoreJudged`, `setAsideOnce`, `restoreProjectionsInTx`) answer `refused` with `could not be checked for an open merge or rebase (...)`, which every caller already reads as "nothing moved" (a throw would set the repository to `error` on a refresh); `resyncHaiveProjections` answers false with a warning, and so does `settleProjections` through it, because their callers rely on them never throwing and the raised marks finish the job. A git dir outside the checkout (a gitfile, or a folder nested in another repository) still reads as open. The `rev-parse --abbrev-ref HEAD` branch reads of the steps above no longer do: `00a-sync-base`, `12-worktree-cleanup` and `13-onboarding-push` throw on a read that gave no answer, and `99-run-app-ready` and `01-worktree-setup`, which must not fail, record `branchError` / `currentBranchError` and show one warning note (99 withholds the push; 01 says the worktree would branch from `main` when no earlier step recorded a base).
