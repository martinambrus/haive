# Secret and git-data masking

Secret-file masking (default on, Tier 1): before each cli-exec invocation the worker hides files matching a secret deny-list from the AI CLI agent by bind-mounting empty read-only files over them inside the cli-exec sandbox (`packages/worker/src/queues/cli-exec/secret-mask.ts`, threaded via `resolveSecretMasks` in `exec-core.ts` for the `cli`/`agent_mining`/sub-agent kinds). The effective set is `DEFAULT_SECRET_DENY_GLOBS` (in `@haive/shared`) plus per-repo `secret_mask_deny_extend`, minus `DEFAULT_SECRET_CARVEOUTS` and per-repo `secret_mask_allow`. Untracked files only (`git ls-files` filter) — committed secrets are out of scope FOR MASKING, and are instead REPORTED once per repo by the `07_7-secret-sweep` onboarding step (which is why they are two features and not one: masking stops an agent reading a secret, the sweep tells the human one is already in their history). The tracked filter asks each linked worktree about its own paths, because `git ls-files` reports paths relative to the tree it runs in, so the repo root never lists `.haive/worktrees/<name>/x`. The app runtime (app-runner/ddev mount the same `haive_repos` subpath without masks) still sees the real files. Per-repo controls live on the tooling settings page (`secret_mask_enabled`/`secret_mask_allow`/`secret_mask_deny_extend`); `CONFIG_KEYS.SECRET_MASK_ENABLED` is the global kill-switch.

Masking fails closed. A scan that throws, a scan root that is not a readable directory, a match count over `SECRET_MASK_LIMIT`, or a task/repository row that cannot be resolved raises `SecretMaskError` instead of masking a partial set — a subset leaves the remainder readable, which is the one outcome the deny-list exists to prevent. "Masking is off" and "no secrets found" are only ever concluded from evidence that says so: the kill-switch, `secret_mask_enabled`, or a task with no repository (which mounts no tree). The repo root mirrors `resolveTaskRepoMount` exactly, so a repo with no `storage_path` is scanned at its named-volume subpath rather than skipped, and the root is `stat`ed before the scan — glob answers `[]` for a root that does not exist, which is byte-identical to a clean repo, while the sandbox mount binds the real tree regardless of what the worker can see. `handleCliExecJob` records it on the invocation (exit -1) and fails the step. The escape hatches are the repo's `secret_mask_allow` globs and the masking toggles; disabling masking skips the scan and never raises.

Git-data masking (always on): every agent prompt states that git is unavailable inside the sandbox and that the host stages and commits (`10-gate-3-commit`, `completeMergeHostSide`). That invariant is enforced, not incidental, and `repoGitDataBoundary` (`packages/worker/src/queues/cli-exec/gitfile-mask.ts`) is the one place that decides the shape it takes. It rides the same `SandboxExtraFile` mechanism as secret masking but is an integrity control, so `SECRET_MASK_ENABLED` never disables it and it has no switch of its own.

A WORKTREE invocation gets an empty read-only file over its `.git` gitfile. Without it an agent can repoint the gitfile at the container path (`printf 'gitdir: /haive/workdir/.git/worktrees/<name>' > .git`), which both grants itself a working git behind the commit gate and leaves host-side git fatally broken for every later step. `removeWorktreeDir` runs `git worktree repair` before removal so worktrees poisoned before this existed still clean up.

A REPOSITORY-ROOT invocation gets the real `.git` DIRECTORY mounted back over itself read-only, through the nested-subpath mount `resolveTaskUploadsMount` already uses. That is every invocation of a task with no worktree — every onboarding step, the steps before `01-worktree-setup`, every plan task, a `kb_author` task with a repository, every same-branch merge fixer — where the whole checkout is mounted read-write and `.git/hooks` and `.git/config` are uid 1000, the sandbox user. Three shapes from ONE no-follow lstat: a directory mounts, a gitfile or a link masks (a mount cannot express a link), and an ABSENT `.git` does NEITHER — docker refuses a subpath that does not exist, and a read-only tmpfs over a missing destination leaves a root-owned stub on the host that would break `12-post-onboarding`'s own `git init`. Applied to every cli-exec kind (both sub-agent kinds included), to `01b-install-plugins`, which reaches `runInSandbox` directly, to the task Terminal and to the browser IDE; the mount target is derived from the mount, so the same function serves `/haive/workdir` and the IDE's `/workspace`. The task shell's fresh-spawn `chown -R` walks AROUND it (`chownCmd`): a plain recursive chown exits non-zero there and that failure is only logged, so it would read as "writes may be denied" for the whole workspace.

The REPO-scope Terminal is the one surface that keeps a writable `.git`, because committing and pushing from there is what it is for (`repos/[id]/terminal`). The app runner and the DDEV runner keep their unmasked view of the tree so the running app's own tooling works — but each mounts only ONE repos-volume subpath (`RUNNER_SUBPATH_LABEL` records which, and a reuse whose resolved subpath differs recreates the container), where both used to mount the whole volume and so every user's repository. That subpath, and the IDE's, is resolved from `tasks.worktree_path` (`resolveDdevWorkspace`) before 01's output, since a Retry nulls the output while the worktree and everything mounting it stay, and a root answered then re-targeted the runner and dropped its database. Only the ensure functions act on that label, so a step execs into a runner only after an ensure in the same pass (`ensureAppServing`, `ensureDdevWithProgress`), never through a handle rebuilt from the task id alone (`runnerHandleForTask`), which checks neither that the runner exists nor which subpath it booted with: a runner gone since 01c answered every such exec with "No such container", which 06a read as an uninstalled site and 08 as a failing check worth a fix round. A probe that must never boot a runner (08b's preflight, the browser runtime, the ddev control queue, app reach) is the exception. A Stop during an ensure is a `TaskCancelledError`, and every best-effort catch around one rethrows it, since the step runner tells a Stop from a failure by that class alone. A worktree's gitfile names an absolute host path that exists in NO container, so git in a worktree cwd never worked in the terminal, the IDE or the runners; only the parent checkout's did.

Host-side git is the other half, and it is what makes an unwritable `.git` less load-bearing than it sounds: every host git argv is built by `hardenGitArgs` (`@haive/shared/git-args`, applied by `repo/git-exec.ts` and asserted by `git-exec-guard.test.ts`), which overrides every key git can be told to execute — `core.hooksPath`, `core.fsmonitor`, `credential.helper`, `core.sshCommand`, gpg signing, the pager — and adds the two flags `-c` cannot express: `--upload-pack`/`--receive-pack` (MEASURED on git 2.54.0: a repository's `remote.<name>.uploadpack` survives `-c`) and `--no-ext-diff --no-textconv` on the diff subcommands (`-c diff.external=` does not disable an external diff, it makes git run the empty string and exit 128). `GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_GLOBAL` are deliberately NOT used: they drop the images' `safe.directory=*` and every call then fails with dubious ownership. What has no lever is a `filter` or `merge` driver named by `.git/info/attributes`, which is exactly why that file is read-only wherever an agent runs. A branch name a person types (00a's base, 01's legacy base) is held to git's own branch-name rules (`isBranchName`, beside `hardenGitArgs`) before any argv carries it, and every fetch of a named branch passes it after `--end-of-options`, fully qualified as `refs/heads/<name>`: a name git accepts can still start with `+`, which an unqualified refspec reads as a forced fetch of another branch.
