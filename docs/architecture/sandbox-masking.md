# Secret and git-data masking

Secret-file masking (default on, Tier 1): before each cli-exec invocation the worker hides files matching a secret deny-list from the AI CLI agent by bind-mounting empty read-only files over them inside the cli-exec sandbox (`packages/worker/src/queues/cli-exec/secret-mask.ts`, threaded via `resolveSecretMasks` in `exec-core.ts` for the `cli`/`agent_mining`/sub-agent kinds). The effective set is `DEFAULT_SECRET_DENY_GLOBS` (in `@haive/shared`) plus per-repo `secret_mask_deny_extend`, minus `DEFAULT_SECRET_CARVEOUTS` and per-repo `secret_mask_allow`. Untracked files only (`git ls-files` filter) — committed secrets are out of scope FOR MASKING, and are instead REPORTED once per repo by the `07_7-secret-sweep` onboarding step (which is why they are two features and not one: masking stops an agent reading a secret, the sweep tells the human one is already in their history). The tracked filter asks each linked worktree about its own paths, because `git ls-files` reports paths relative to the tree it runs in, so the repo root never lists `.haive/worktrees/<name>/x`. The app runtime (app-runner/ddev mount the same `haive_repos` subpath without masks) still sees the real files. Per-repo controls live on the tooling settings page (`secret_mask_enabled`/`secret_mask_allow`/`secret_mask_deny_extend`); `CONFIG_KEYS.SECRET_MASK_ENABLED` is the global kill-switch.

Masking fails closed. A scan that throws, a scan root that is not a readable directory, a match count over `SECRET_MASK_LIMIT`, or a task/repository row that cannot be resolved raises `SecretMaskError` instead of masking a partial set — a subset leaves the remainder readable, which is the one outcome the deny-list exists to prevent. "Masking is off" and "no secrets found" are only ever concluded from evidence that says so: the kill-switch or `secret_mask_enabled`. A task with no repository has no repository policy, but its scratch workspace (`_scratch/<taskId>`, which `kb_author` and repo-less custom types run in) is still mounted, so it is scanned with the default deny-list; only an invocation with no mount at all returns no masks. The repo root mirrors `resolveTaskRepoMount` exactly, so a repo with no `storage_path` is scanned at its named-volume subpath rather than skipped, and the root is `stat`ed before the scan — glob answers `[]` for a root that does not exist, which is byte-identical to a clean repo, while the sandbox mount binds the real tree regardless of what the worker can see. `handleCliExecJob` records it on the invocation (exit -1) and fails the step. The escape hatches are the repo's `secret_mask_allow` globs and the masking toggles; disabling masking skips the scan and never raises.

Git-data masking (always on): every agent prompt states that git is unavailable inside the sandbox and that the host stages and commits (`10-gate-3-commit`, `completeMergeHostSide`). That invariant is enforced, not incidental, and `repoGitDataBoundary` (`packages/worker/src/queues/cli-exec/gitfile-mask.ts`) is the one place that decides the shape it takes. It rides the same `SandboxExtraFile` mechanism as secret masking but is an integrity control, so `SECRET_MASK_ENABLED` never disables it and it has no switch of its own.

A WORKTREE invocation gets an empty read-only file over its `.git` gitfile. Without it an agent can repoint the gitfile at the container path (`printf 'gitdir: /haive/workdir/.git/worktrees/<name>' > .git`), which both grants itself a working git behind the commit gate and leaves host-side git fatally broken for every later step. `removeWorktreeDir` runs `git worktree repair` before removal so worktrees poisoned before this existed still clean up.

A REPOSITORY-ROOT invocation gets the real `.git` DIRECTORY mounted back over itself read-only, through the nested-subpath mount `resolveTaskUploadsMount` already uses. That is every invocation of a task with no worktree — every onboarding step, the steps before `01-worktree-setup`, every plan task, a `kb_author` task with a repository, every same-branch merge fixer — where the whole checkout is mounted read-write and `.git/hooks` and `.git/config` are uid 1000, the sandbox user. Three shapes from ONE no-follow lstat: a directory mounts, a gitfile or a link masks (a mount cannot express a link), and an ABSENT `.git` does NEITHER — docker refuses a subpath that does not exist, and a read-only tmpfs over a missing destination leaves a root-owned stub on the host that would break `12-post-onboarding`'s own `git init`. Applied to every cli-exec kind (both sub-agent kinds included), to `01b-install-plugins`, which reaches `runInSandbox` directly, to the task Terminal and to the browser IDE; the mount target is derived from the mount, so the same function serves `/haive/workdir` and the IDE's `/workspace`. The task shell's fresh-spawn `chown -R` walks AROUND it (`chownCmd`): a plain recursive chown exits non-zero there and that failure is only logged, so it would read as "writes may be denied" for the whole workspace.

The REPO-scope Terminal is the one surface that keeps a writable `.git`, because committing and pushing from there is what it is for (`repos/[id]/terminal`). The app runner and the DDEV runner keep their unmasked view of the tree so the running app's own tooling works — but each mounts only ONE repos-volume subpath (`RUNNER_SUBPATH_LABEL` records which, and a reuse whose resolved subpath differs recreates the container), where both used to mount the whole volume and so every user's repository. That subpath, and the IDE's, is resolved from `tasks.worktree_path` (`resolveDdevWorkspace`) before 01's output, since a Retry nulls the output while the worktree and everything mounting it stay, and a root answered then re-targeted the runner and dropped its database. Only the ensure functions act on that label, so a step execs into a runner only after an ensure in the same pass (`ensureAppServing`, `ensureDdevWithProgress`), never through a handle rebuilt from the task id alone (`runnerHandleForTask`), which checks neither that the runner exists nor which subpath it booted with: a runner gone since 01c answered every such exec with "No such container", which 06a read as an uninstalled site and 08 as a failing check worth a fix round. A probe that must never boot a runner (08b's preflight, the browser runtime, the ddev control queue, app reach) is the exception. One runner serves the task's own tree, so an invocation mounted on another worktree (a DAG issue coder, a merge fixer) is told in its app-reach block that the app shows none of its changes (`appServesOtherTree`). A Stop during an ensure is a `TaskCancelledError`, and every best-effort catch around one rethrows it, since the step runner tells a Stop from a failure by that class alone. A worktree's gitfile names an absolute host path that exists in NO container, so git in a worktree cwd never worked in the terminal, the IDE or the runners; only the parent checkout's did.

Host-side git is the other half, and it is what makes an unwritable `.git` less load-bearing than it sounds: every host git argv is built by `hardenGitArgs` (`@haive/shared/git-args`, applied by `repo/git-exec.ts` and asserted by `git-exec-guard.test.ts`), which overrides the keys git can be told to execute that Haive's own command mix reaches — `core.hooksPath`, `core.fsmonitor`, `credential.helper`, `core.sshCommand`, `core.askPass`, `core.alternateRefsCommand`, `protocol.ext.allow`, `protocol.git.allow`, `protocol.file.allow` (on every transport verb: `clone`, `fetch`, `pull`, `push`, `ls-remote` and `remote update`, whatever the remote is called; the host-folder refresh is the one call that opts in with `allowFileTransport`), gpg signing and the config switches that start a gpg run (`log.showSignature`, `merge.verifySignatures`, `push.gpgSign`, `tag.forceSignAnnotated`), the editors (`core.editor`, `sequence.editor`), submodule recursion (`submodule.recurse`), automatic maintenance (`maintenance.auto`) and the pager — and adds the two flags `-c` cannot express: `--upload-pack`/`--receive-pack` (MEASURED on git 2.54.0: a repository's `remote.<name>.uploadpack` survives `-c`) and `--no-ext-diff --no-textconv` on the diff subcommands (`-c diff.external=` does not disable an external diff, it makes git run the empty string and exit 128). `GIT_CONFIG_NOSYSTEM` and `GIT_CONFIG_GLOBAL` are deliberately NOT used: they drop the images' `safe.directory=*` and every call then fails with dubious ownership. What has no lever is described two paragraphs down, and it is why `.git/info/attributes` is read-only wherever an agent runs. A branch name a person types (00a's base, 01's legacy base) is held to git's own branch-name rules (`isBranchName`, beside `hardenGitArgs`) before any argv carries it, and every fetch of a named branch passes it after `--end-of-options`, fully qualified as `refs/heads/<name>`: a name git accepts can still start with `+`, which an unqualified refspec reads as a forced fetch of another branch.

The second set of overrides was MEASURED on git 2.43.0 (the dev host's) and 2.54.0 (the images'), with the same outcome on both, against a repository whose own config named a marker-writing script for each key; `git-config-program-keys.test.ts` holds one row per key, and each row first proves with plain git that the marker is written. An EMPTY `core.askPass` is what stops the repository's askpass program, which runs on any 401 or proxy prompt that no credential helper answered: a trusted `GIT_ASKPASS` (`gitClone`'s spawn and the three bundle `gitRun` callers that pass `GIT_ASKPASS=echo`) still wins, an `SSH_ASKPASS` fallback is no longer consulted (nothing here sets one), and the stored credential keeps working because `buildCredentialHelper` answers before any prompt. `core.gitProxy` runs a command for a `git://` remote and `-c core.gitProxy=` does NOT override it (git keeps the FIRST matching entry, and the repository's own precedes the command line); `GIT_PROXY_COMMAND=` would, but only reaches `gitRun` and `gitExec`, so `protocol.git.allow=never` is the lever, which also matches the product's URL allowlist (`git://` is unsupported, `schemas/git-url.ts`). A repository can enable the `ext::` transport itself (`protocol.ext.allow=always`, directly or through `url.<base>.insteadOf`), so it is forced to `never`. `core.alternateRefsCommand` runs on a fetch into any repository that has `objects/info/alternates`; an empty command lists no refs. An editor is a command too: `core.editor` runs for a `commit` without a message and for `merge --continue`, `sequence.editor` for `rebase -i`, and git treats `:` as no editor, so both are forced to it (a plain merge whose stdout is a pipe never opens one, MEASURED; every Haive commit passes `-m`, `-F` or `--no-edit`, so this is a backstop). A log, show, merge or push of a commit that carries a signature header runs `gpg.program` (or the x509 and ssh programs, chosen by the header's armour) once the repository's config switches verification on, and `tag.forceSignAnnotated` is a different key from `tag.gpgsign`, so all four switches are forced off. A repository's `gc.recentObjectsHook` runs inside automatic maintenance after `commit`, `merge`, `fetch` and `pull` as soon as its config names a strategy that runs `gc` (git 2.54's default strategy does not, 2.43's does) and it holds aged unreachable objects; `-c gc.recentObjectsHook=` APPENDS an empty command instead of resetting the list, so the trigger is what `maintenance.auto=false` switches off, at the price that Haive's own git calls never start a `gc` (a person's own git use of the checkout is unaffected). A fetch, pull or push recurses into registered submodules by default, and the child git it starts for a submodule takes none of the per-subcommand flags, so a submodule's own `remote.origin.uploadpack` or `receivepack` ran; `submodule.recurse=false` is the lever for all three, because it is read last (`fetch.recurseSubmodules=no` alone does not stop a push, or a pull whose config sets `submodule.recurse=true`), and Haive never needs a submodule's objects on the host.

Measured to run under the hardened argv but not reachable from Haive's own calls, so left alone: `pager.<cmd>` (only under a TTY, and stdout is always a pipe here), `diff.<driver>.textconv` under `blame`, `reflog -p` and `range-diff`, a `%G?` placeholder, an explicit `gc` or `prune`, an explicit `submodule update` with a `!command` (nothing else runs it, `--checkout` stops it, and only `submodule foreach` with a fixed command is used), and `git archive` with a `tar.<format>.command`. A caller that starts to use one of them adds its lever first. Not executed at all: `uploadpack.packObjectsHook` from a repository's own config (git reads it from protected scopes only) and an `alias` named like a builtin. Several classes have no complete lever through `hardenGitArgs`. A `filter.<driver>.clean`, `smudge` or `process`, or a `merge.<driver>.driver`, named in the repository's own config and selected by a tracked `.gitattributes` or by `.git/info/attributes`, runs under `add`, `checkout` and `merge` with the hardened argv (MEASURED, and end to end: an archive that ships such a config comes through `extractArchive` untouched and `gitRun(['add', '-A'])` runs the program); driver names are open-ended, so no `-c` list covers them, and the position that nothing can write `.git` does not hold for an uploaded archive that ships its own `.git/config`. A `remote.<name>.vcs` naming a path (`../x` makes git run `git-remote-../x` relative to the working tree, where the repository can ship an executable) is stopped by a protocol allowlist only until the repository sets `protocol.<that name>.allow=always` itself; only the trusted `GIT_ALLOW_PROTOCOL` environment variable holds (MEASURED), and listing `file` in it also lets a submodule's local-path URL through, which git's default refuses. A partial clone (`extensions.partialclone` with a promisor remote) runs its `remote.origin.uploadpack` when a command needs an object it lacks; `GIT_NO_LAZY_FETCH=1` stops that and also breaks real partial clones. `fetch --all`, `fetch --multiple` and `remote update` start a child per remote that takes none of the per-subcommand flags (no Haive service or script calls them; the two operator scripts fetch `origin` through `originGitRun`, and `origin-exec-guard.test.ts` scans the scripts too). And `-c` does not reach the program git spawns for a LOCAL-PATH remote (MEASURED: no `GIT_CONFIG_PARAMETERS` in the spawned `git-receive-pack`'s environment), so a push to a local-path origin would run the TARGET repository's hooks and `core.alternateRefsCommand` with no hardening. Every network git call on `origin` therefore validates the origin's fetch and push URLs first (`originGitRun`: https, http, ssh or scp-style only, never a `<transport>::<address>` remote-helper spelling) and refuses the file transport, every `clone` checks its stored URL the same way before it touches the old tree (`assertCloneUrl`), and a relink clears every push URL before it replaces every fetch URL, so no Haive call reaches a local-path origin; the host-folder refresh of a local repository fetches by path on purpose ([Repository refresh](repository-refresh.md)).

Git credentials use the stored remote as their binding. Repository and bundle creation both
check credential ownership and `credentialFitsGitRemote` before persisting or queueing; the
one-shot helper answers only `get` with the bound protocol and authority. A local-folder import
without a stored remote uses the sanitized origin persisted in the user's approved push form,
never a fresh origin read. `getOriginUrl` returns binding identity: userinfo is removed from
HTTP URLs, SSH keeps its non-secret login, and explicit default ports remain spelled out because
Git's credential challenge keeps `:443` and `:80`. `gitRemoteIdentity` omits query and fragment
values from saved approvals while keeping that authority spelling; display labels separately use
`redactGitUrl`'s display policy. PR origin stamps and legacy poll fallbacks preserve the same
sanitized identity.

`redactGitText` removes userinfo even when a legacy diagnostic URL contains quote, angle-bracket
or backtick characters in its authority; those characters delimit display text only after the
userinfo. A quoted legacy URL also keeps whitespace inside its userinfo; unquoted whitespace
separates prose. `scrubSecret` replaces a known intact secret before rewriting URLs, since rewriting
first can destroy the match and expose a suffix. Legacy bundle onboarding forms, bundle API diagnostics and repository
refresh queue payloads redact their own reads, including failed bundles that never reach sync.
This protects new copies of old rows; it does not rewrite historical rows or prior step outputs.

`git-exec-guard.test.ts` finds a spawn by its first argument, never by the name of the function that carries it: any `<name>('git', …)` in the worker, api and shared sources, the worker's `scripts/` and every module's sources must pass `hardenGitArgs(…)` as the argv, so an alias such as `promisify(execFile)` hides nothing (the learning and skill-sync steps once spawned git through one). A text scan cannot see a git command held in a variable or run through a shell string, so neither is used, and a new package that runs git needs its sources added to the guard's `scanRoots`. `child-process-ratchet.test.ts` (`@haive/shared`) covers what the scan cannot see: over every package and the root `scripts/` it pins, per file, each `child_process` call whose command is not provably a plain non-git program (a variable, a shell string, a path to git, a shell wrapper, a literal `git`), so a new one lands where a reviewer sees it. The reach of the unhardened form was MEASURED on git 2.43.0, the dev host's (the reproductions pin it on whichever git runs the suite): a registered submodule's own `core.fsmonitor` runs under `git status` only when the status pathspec reaches the submodule (the learning gate's `.haive-data/knowledge_base` does, once one is registered there), `add`, `commit`, `show` and `rev-parse` do not run it, and a repository's hooks run on `commit`. The reproductions in `11-phase-8-learning.test.ts` and `11d-skill-sync.test.ts` are shaped by that: a marker file written by the monitor script or the pre-commit hook must not appear.

Every host git run is also bounded in time: a caller's own `timeout` wins (`0` means none), and otherwise `gitDefaultTimeoutMs` gives 30 min to `clone`, `fetch`, `pull`, `push`, `ls-remote`, `gc`, `repack`, `prune`, `fsck`, `merge`, `rebase`, `cherry-pick`, `submodule` and `lfs`, and 10 min to everything else, so a hung credential helper or a stale mount ends the step instead of holding it. A run killed by the bound returns code 124 from `gitRun` (never git's own 1) with `git <subcommand> timed out after N s` as its last stderr line, and `gitExec` throws with that message. A run that ends with no exit status at all (git could not start, a missing cwd included; a signal other than the bound; an output past the buffer) returns `GIT_NO_EXIT` (-1), never 1, with the cause in `noExit` and `git ended without an exit status in <cwd> (<cause>)` as its last stderr line, so a reader that takes exit 1 for "no" never takes it for an answer. `gitGaveNoAnswer` names both (no exit status, or the bound's 124): a reader that turns a non-zero exit into "no", "absent", "clean" or "not usable" checks it first and throws or holds, never answers; a step that must not fail records the reason and shows it as a note instead. Streaming callers that `spawn` git themselves are not covered; the bundle resync, ingest and daily sync go through `gitRun` and are.

The `.haive-data` boundary (always on, agent sandboxes only): `haiveDataBoundary` (`packages/worker/src/queues/cli-exec/haive-data-boundary.ts`) mounts `.haive-data/` READ-ONLY into every agent sandbox, at a repository root and in a worktree, then mounts `knowledge_base/` and `learnings/` back read-write. The rest of that tree is Haive's record and plan (`state/**`, `plan.json`, `plan.md`), and every working-tree reader (the sync, the set-aside, the plan mirror, the sweep) imports what it finds there as genuine, so an agent must not be able to write it at all. The two knowledge dirs stay writable because agents write them on purpose: 09_3's KB corrections, the merge fixers' KB conflicts, 01e and 11 in a worktree, and the learnings agent's one new file per lesson. It rides beside `repoGitDataBoundary` in every cli-exec kind (both sub-agent kinds included), in step commands (`runStepCommandInSandbox`) and in `01b-install-plugins`; the Terminal and the IDE are people's surfaces and keep a writable `.haive-data`. Masking step commands was chosen over leaving the record writable to the project's own tooling, so a formatter run in write mode over the whole tree fails on the JSON there.

The whole directory is the unit because nothing narrower holds. MEASURED on Docker 29.8.2: with `.haive-data` read-only and `knowledge_base/` read-write, writes and creates under `state/` and the plan files fail (EROFS), `mv .haive-data` fails (EBUSY), KB writes work, and host-side rewrites underneath do not detach the mount; a mount of `state/` alone is beaten by `mv .haive-data` plus a forged `state/`, and per-file plan mounts are dropped by the mirror's own rename-over rewrites. Docker refuses a subpath that does not exist, so a missing `.haive-data/` and `learnings/` are created first, owned like the mount root. `knowledge_base/` is NEVER created there, because it is an onboarding marker: a missing one gets no mount, and so does a child that is a file or a link, which the read-only parent keeps an agent from replacing. A `.haive-data` that is itself a file or a link, or a mount root that is not a directory, refuses the run instead, since an agent could put a directory of its own in its place; docker's volume subpath follows a relative link inside the volume (MEASURED), so a worktree path turned into a link would otherwise mount the tree it points to with no boundary at all. A protected file with more hard links than names in the read-only part refuses the run too: an agent cannot make a new link across the mounts (`Cross-device link`, MEASURED), but one made before the boundary existed, from the checkout or a knowledge dir, lets it rewrite the record through that other name. Nothing created is ever removed: removing a stub after one run detached the mounts of sibling runs. Every lookup is a no-follow lstat walked from the repository-root anchor (`lookupInRepoMount`, which `repoGitDataBoundary` shares), so a worktree subpath is split into `<userId>/<repoId>` plus a relative prefix, and a malformed subpath throws instead of being looked up.

The worktrees boundary (always on, agent sandboxes mounted at the repository root only):
`worktreesBoundary` (`packages/worker/src/queues/cli-exec/worktrees-boundary.ts`) mounts
`.haive/worktrees` READ-ONLY. A sandbox at the root (onboarding, steps before `01-worktree-setup`,
plan tasks, `kb_author`, same-branch merge fixers) otherwise holds every other task's writable
worktree. It also mounts `.haive` onto itself read-write. A mount point cannot be renamed, so
`mv .haive` cannot move the real worktrees aside and plant new ones, and `.haive/kb-draft/` stays
writable. A worktree invocation mounts the worktree itself, so it needs neither.

MEASURED on a throwaway volume:

- Writes, creates, links, `rm -rf` and `mv` of `.haive/worktrees` fail.
- `mv .haive` fails with EBUSY.
- `kb-draft` and repository-root writes work.
- A `mv` of the worktrees to a sibling only copies them, which reading allows anyway. `.haive` is a
  mount of its own, so a rename between it and the rest of the tree is cross-device: `mv` copies,
  and a bare `rename(2)` gets EXDEV.

A missing `.haive/worktrees` is created first, owned like the root, so a worktree added later
appears inside the read-only mount. A `.haive` or `.haive/worktrees` that is a file or a link
refuses the run. The check and the mount are separate steps, the same window the `.haive-data`
boundary has.

The boundary does not look for hard links, unlike the `.haive-data` one. A worktree is a full
checkout, often with `node_modules`, so an inode count over every worktree would walk tens of
thousands of files on every root-mounted invocation. No new link can be made across the mounts
(`Cross-device link`, the same mount shape `.haive-data` measured). A link a root-mounted agent
planted before the boundary existed survives, though: an alias of a worktree file in the writable
checkout stays writable.

Step 11 asks its agent to edit the knowledge base on every task, and a blank repository has no `knowledge_base/` by design. So in a task worktree its `prepare` creates the directory, owned like the worktree root, before the agent runs; an empty directory is never committed, so it cannot fake the marker. At the repository root (01 skipped) it creates nothing: it skips the KB-sync half and offers no local investigation (a global promotion still works), and records why in `kbSyncSkipped`.
