Full-Workflow LLM Benchmark — “Add DDEV”

One multi-day, 40-step implementation workflow — technical spec, spec audit, spec-quality gate, sprint planning, DAG execution, implement, validate, verify, test management, security / operational / peer code review, broad code audit, hands-on developer verification, commit gate, learning capture and knowledge-base writes — run end to end against the same legacy PHP 4/5 CMS across 19 models and every reasoning-effort level. 60 runs reached a commit.

Unlike the README benchmark, the artifact here is not a document: it is a working development environment plus whatever the model decided the repository also needed. Every run was graded on what it shipped, what it broke, what it caught, what it cost and what it left behind for the next run.

02Delivery: did the app actually work?

Gate 2 is a human sitting in front of the running site in a browser. It is the only judge that cannot be gamed, and it is where this task turned out to be hard: the CMS ships a getBack2HTTP() helper (thememanager.php) that emits JavaScript forcing the URL back to http://, which fights DDEV's HTTPS-forcing router into an infinite reload, and one preg_replace() /e-modifier call site (actions/admin_remove_cpage.php) that emits a deprecation notice on the homepage. Everything else was self-inflicted.

03The artifact: what actually landed

Every run produced a valid .ddev/config.yaml pinned to PHP 5.6 / MariaDB 10.11 (58 of 60 chose apache-fpm, 2 chose nginx-fpm) — that part is commoditised and discriminates nothing. What separates the field is where each run chose to solve the legacy runtime problems, and what it left behind.

Containment — fix it at the environment boundary

An auto_prepend_file or php.ini under .ddev/ that neutralises the protocol-flipping JavaScript and the deprecation notice without editing a line of 2008 application code. This is the answer the workflow's own knowledge base converged on — three separate runs wrote global entries saying so, including “Do not ‘modernize’ deprecated syntax in dual-version-compatible legacy PHP” and “Patch a legacy PHP app's runtime behaviour from the container config”.

Rewrite — fix it in the application

Edit thememanager.php, functions.php, the installer, the backup module. Works, but it changes production behaviour for a dev-environment ticket. At the extreme, Codex gpt-5.6-sol at high modified 60 application PHP files and at ultra added a 1,264-line content_delete_guard.php and a 758-line alias_mutex.php the specification never asked for.

04Does more reasoning effort buy a better result?

On this task, no — and the cost of finding that out was enormous. The cross-family averages below can be skewed by which models happen to sit in each tier, so the decisive test is within a model: comparing every pair of runs of the same model at two different effort settings, the higher setting produced the better composite score in only 37 of 97 pairs (38%). It lost nearly two head-to-heads in three against itself at a lower setting, while CLI time and token spend rose monotonically with effort in nine of the eleven models with four or more levels.

There is one clean counterexample, and it is worth naming: Haiku 4.5 is the only model where effort visibly rescued the run. At low, medium and high it needed 8, 9 and 7 rejection rounds and never delivered; at xhigh and max it needed 2. Effort buys the most where raw capability is the binding constraint — and the least where it is not.

Read this one carefully. Reasoning effort is not wasted — it buys real depth, and §06 shows the high-effort runs finding four to sixteen times more critical/high issues per review pass than the field median. What it does not buy on a scoped infrastructure task is a finished job. The three highest-effort Codex runs (high, max, ultra) spent 19–33 h of CLI wall clock and 79–114 M tokens each, and two of the three were closed by force with the site still returning a PHP memory-exhaustion fatal.

05Cost, time, and how both were measured

Two things had to be removed before any time comparison was honest: retries caused by workflow bugs (not the model's fault) and human thinking time at the gates (also not the model's fault, and it dominates the raw clock — 4,794 h of it across the sweep, against 319 h of actual CLI work).

The clock used here

Sum of the merged (overlap-collapsed) start→end intervals of every CLI invocation whose superseded_at is null. Superseding is what the engine stamps when an invocation is orphaned, killed, re-dispatched after an infrastructure failure, or discarded by a manual step retry — exactly the retried work that must not be charged to the model. 97 h of retry time was excluded this way. Fix-loop rounds are not excluded: redoing work because your own review or the developer rejected it is the model's own cost.

The token unit

Providers do not agree on what input_tokens means: Anthropic-wire families report it exclusive of the cache buckets, Codex reports it inclusive of the cached prefix, and Ollama reports no cache at all. Raw totals are therefore not comparable. Billed-equivalent tokens normalises this: fresh input + output + 10% of cache reads + 125% of cache writes, with the cached prefix subtracted from Codex's input first. It is a cost proxy, not an invoice.

Billed-equivalent tokens (log scale) against composite score. The upper-left quadrant is where you want to be.

06Rigor: who found the security and operational problems

Each run fans out five reviewer roles over its own change set — security-code-reviewer, operational-reviewer, peer-reviewer, validator and a broad code-auditor — and a three-lens refuter panel tries to disprove every blocking finding before it costs a fix round. Across the sweep those roles raised 8,869 findings, 2,473 of them critical or high.

The reviewer prompts in this workflow are known to be too broadly scoped, which is why the strongest models audited the entire repository rather than only the change set. That is treated here as a property of the harness, not a fault of the model: depth is scored as a strength. The reverse is scored too — a model that could have run the same analysis at its own depth and did not is marked down for it, and that is what separates the shallow runs at the bottom of the Rigor column from the merely fast ones.

Critical/high findings per review round. The field median is 1.9. Noise is tracked separately: the percentage of blocking findings that the refuter panel overturned.

07Knowledge: what each run left for the next one

Two knowledge surfaces are in play. Repo-local learnings under .claude/learnings/ (192 written across the sweep) and the cross-repo global knowledge base, where an entry has to survive an embedding-similarity supersede gate to stay active. 36 global entries were promoted by these runs; 29 are still active.

The compounding effect is visible and it is the single largest confound in this benchmark. The first run to explain the reload loop — “App-injected JS HTTPS-to-HTTP downgrades loop forever behind an HTTPS-forcing router” (GLM-5.2 · z.ai, 2026-07-24) — was followed by four more entries on the same failure through 08-07. Runs starting after that point could retrieve the answer instead of rediscovering it. The KB era and the model generation move together, because the newest models were also tested last: Opus 4.6, GLM-5.3 and Grok only ever ran in the mature-KB window. The two cannot be separated from this data set, so both are shown and neither is silently corrected away.
