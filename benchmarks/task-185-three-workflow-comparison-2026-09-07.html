Three workflows, one task — TASK-185
Selective PDF field visibility across the four gas inspection forms

The same customer request was implemented three times from a comparable base commit: once by the legacy markdown-driven Claude Code /workflow (August 2026), and twice by Haive in September 2026 — once driven from a repository plan, once from a bare task description. This grades what each one actually shipped, what it cost, and where the differences come from.

A’s suite has the best architecture of the three: a descriptor table (tests/utils/inspection-types.ts, 363 lines) drives one parameterised spec across all four form types and both sections of each, plus per-type baseline HTML fixtures and a shared pdf-debug.ts harness. B duplicates a similar spec four times. The old run sits in between with five specs over one shared util. On assertion quality A is also cleanest — lower-bound assertions (toBeGreaterThanOrEqual) are the exact anti-pattern the old run wrote into the repo’s TESTING_STANDARDS.md because they pass while items are missing, and A uses a third as many proportionally as either alternative. Two of these counts are self-validating: the old run’s commit message claims “24 Playwright tests” and B’s own 08b step reported “all 32 tests load cleanly”, which is exactly what the trees measure.

None of that was worth anything, because A never ran it. Every fix-loop round in both Haive runs was triggered by 08b-test-management, and every one of them turned out to be an invocation or environment problem rather than a defect:
  • A r1, A r2, B r1 — Error: Playwright Test did not expect test.describe() to be called here. The runner was invoked from the docroot, where there is no playwright.config.ts, so the spec was evaluated outside its collection phase. B additionally recorded that npx then fetched playwright 1.63.0 while the specs import 1.54.1.
  • A r3 — chromium.launch() in global-setup.ts: “Playwright’s browser binaries are not installed in the DDEV web container: /home/ddev/.cache/ms-playwright/chromium_headless_shell-1181 is absent.”
  • A r4, B r2 — no run attempted; both steps audited the specs statically and returned no verdict.
Each of those rounds burned 5 internal fix passes first: 15 wasted passes in A, 5 in B. The old workflow’s equivalent phase failed once, was fixed by a playwright-tester agent, and then completed twice.

05Process & rounds

Where A’s four rounds went

  • Round 0 → 1 — developer rejected at Gate 1: “resolve the points listed in quality review”. Spec rewritten, re-audited, approved (quality score 9).
  • Round 1 → 2, 2 → 3, 3 → 4 — three identical fix_loop.requested events, all sourced from 08b-test-management, all reading “The related tests still fail after 5 fix pass(es)…”.
  • In every one of those rounds 07-phase-2-implement was skipped — so no agent ever read the diagnosis, and the whole review chain re-ran against unchanged code.
That last item is a since-fixed harness bug, not a property of the plan. In DAG mode 07 used to skip at every round. Its shouldRun now splits by round (mode !== 'dag' || ctx.round > 0) and the fix’s own source comment names this task: “task 681f0f99 spent 3 rounds that way, each recording a fix_loop.requested nothing consumed.” Read A’s round count as 1 real round plus 3 that the orchestrator could not have used.

Where the old run’s two rounds went

  • Phase 4 validator, Phase 5 browser test, Phase 6 peer + security review all passed — while 10 fields had no checkbox at all.
  • Gate 2 — the developer found all 10 by eye.
  • Fix loop #1 — relocated an existing checkbox instead of adding one, re-creating the reported bug elsewhere.
  • Fix loop #2 — “Fix loop #2: add per-subfield checkboxes”, then a green Playwright regression run.
  • Afterwards, one more human turn: “fix the Ai/Bi section I labels too” → commit af2dbfb8.

The honest one-line answers

  • Which workflow is best as a whole? Haive, run without a plan. It got within 10 checkboxes of an artifact that took a human two rejection rounds to reach, with no defects the human had to find, for 13 minutes of attention and 6.8 hours of elapsed time.
  • Where is the old workflow still ahead? It ran its tests, and it converted the run into durable knowledge and a new reviewer role. Both are things Haive should be able to do and did not.
  • Did the plan help? On analysis, decomposition and test architecture, clearly yes. On the code that shipped, no — it cost 2.0× the tokens and 2.1× the wall clock and delivered the worse artifact of the two.
  • Is the Haive workflow an improvement on the original? On process, decisively — auditability, review depth, human cost, and reviewers that find real security defects rather than passing a broken artifact. On verification, it has regressed: the old loop proved its work by running it, and neither new run did.

11Confounds & methodology

  • The two Haive repos are not equally prepared. Repo A was onboarded through Haive (62 tracked artifacts, KB indexed into RAG, 544-node plan). Repo B was never onboarded — 0 artifacts, and its RAG index carries code chunks only. Both trees carry the same 28 on-disk agent definitions and 41 knowledge-base files inherited from the source repo, so B’s agents could read the KB from disk but could not rag_search it. The user’s framing was “plan vs no plan”; the actual difference is “onboarded + planned vs neither”.
  • Different base commits. A and B branch from 05e615e (Merge TASK-179). The old run branched from 655e04bc (Merge TASK-178), one merge later. The 185 work is absent from both Haive bases, so no run could see another’s answer.
  • The old run’s diffstat against its merge base includes unrelated drift (a master→dev difference touching inspection.class.inc, notification_email.class.inc, CRON_JOBS.md). All figures quoted for it come from its own two commits (2a6d8775, af2dbfb8) or from the merge commit’s first-parent stat, not from that diff.
  • Checkbox counts come from '#type'\s*=>\s*'checkbox' over the delivered file, whitespace-insensitive — B aligns its arrows in two files and not the other two, which a naive grep miscounts by 51.
  • The field-coverage table was produced by parsing $form['myform']['part_N']['KEY'] = array(…) blocks out of each delivered file and matching data fields against checkbox keys under three naming conventions (…c, …_show, …_pdf_c). Fields outside the task’s named sections (part_0, part_6, part_7, part_12, part_13) are uncovered in all three runs and are excluded from the comparison.
  • The old run’s timeline was reconstructed from ~/.claude/timings/*.jsonl (a local instrumentation wrapper) across four wrapper sessions carrying claude_session f0eef6b4-6bad-441b-ae18-81a18db9c0cb, cross-checked against ~/.claude/history.jsonl. The session transcript itself no longer exists. The Gate 2 rejection text is not in either log; the two session-memory files written by that run at 2026-08-06T05:52Z are the surviving first-party record and are quoted rather than paraphrased.
  • Nothing here is scored on a run’s self-report. Coverage, accessibility, cache invalidation, scope and test counts were all measured against the delivered git trees. Round counts, findings and costs come from Haive’s Postgres rows.
  • Not measured: whether the delivered PDFs actually render correctly. No run in this comparison produced a green browser verification against all four forms, so functional PDF correctness is asserted by none of them and checked by none of this.
