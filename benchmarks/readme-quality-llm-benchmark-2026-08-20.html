06Methodology & provenance

  • Task shape. One "Add README" quick-fix workflow task per (model, effort), all against a byte-identical copy of the same Redaction System source. Each task's headline model drove every LLM step via ignore_saved_step_clis — read from the tasks row, not assumed: all eleven new tasks carry true.
  • Which runs count. Inclusion is "produced a README", not "task status = completed" — three published rows (1a99485a, 8500e207, 8d2987c9) come from tasks later marked cancelled that had already written and committed their README. All eleven new runs completed normally and committed. One duplicate stays excluded: a second Muse-low task (26cf4a4c) re-ran the same repo an hour after 9de5cb55, finished in five minutes and committed nothing. Six further tasks are excluded as a different task shape — fcf03ead, 42176a51, a96e7dda, eb081ba4, dd682d32 and 73852f1b, all titled "Add DDEV" and completed 8–17 August. Each of them also modified README.md, so a query on changed paths alone would sweep them in, but their prompt is "add a DDEV environment", not "write a README": the README edit is incidental and the artifact is not comparable. This matches the standing exclusion of 16067fcb, 381afc5e and 433a7ea5 on the same grounds.
  • Model identity is read from each run's stream log, not from the task title or the cli_providers.model column. The five Opus 4.6 runs record requested: claude-opus-4-6 / served: claude-opus-4-6; the four GLM runs record requested: glm-5.3[1m] / served: glm-5.3 — the endpoint drops the variant tag, which the invocation's model_identity classifies exact. The two Grok runs predate model_identity capture, so their model was read straight from the stream: the invocation line carries -m grok-4.6 / -m grok-build-0.1 and every "model" field in the streamed messages agrees (13 and 14 occurrences respectively).
  • Validity. For every run the newest 07-phase-2-implement invocation's provider is compared against the task's provider; a mismatch would mean the README was written by a different model than the row claims. All 66 match, and all eleven new implement invocations exited 0.
  • Scoring rubric (unchanged): accuracy = are the claims true of this source tree, completeness = does it cover stack, architecture, domain model, install/config, security posture and credits, clarity = can a newcomer act on it. Security posture means naming what is unsafe, not just listing the controls that exist: opus46-xhigh has a "Security Model" heading listing six controls and scores no credit for it, because not one of the six is a weakness. Composite = accuracy×5 + completeness×3 + clarity×2. Hallucinations counts distinct fabricated facts — invented tables, files, mechanisms, or harness values presented as project reality.
  • Calibration note on clarity. Across all 66 runs clarity has only ever been scored 8 or 9; no README has earned a 10. That makes 98 the effective maximum of this rubric, which is why the top of the table is a three-way tie rather than a ranking, and it is unchanged this edition. Reaching it requires all six coverage dimensions, security posture included — which is what holds Grok 4.6 at 95 despite it being the most factually exact README in 66 runs. Applying the dimension consistently also moved three of this edition's own drafts downward late in the audit (grok-4.6 95 not 98, glm53-high 90 not 93, opus46-high 77 not 80); the precedent is the 3 August deepseek-v4-flash row, docked for exactly this and described there as "the disclosure that separates the 90+ READMEs".
  • Audited from the root commit. Each of the eleven new repositories already carried an onboarding commit before its README task ran, and the README task adds its own. Source facts were therefore checked against a pristine tree exported with git archive from the repository's root commit, and each README was read with git show <tasks.commit_sha>:README.md rather than from the working directory — so a later task cannot alter either side of the comparison.
  • A correction to the companion onboarding report. That report calls opus46-high's rs2_ table prefix a fabrication. It is not fabricated: the project's own TODO file opens with a DB-Updates block written against rs2_forms, rs2_modules, rs2_main, rs2_contents and rs2_ranks — the original author's install prefix, in the tree. The defect is real but it is a wrong generalisation, not an invention: the installer defaults the field to rs_ (installer/contents_step_4.php:41) and the value is operator-chosen, so rs2_ is not "the" prefix. Scored here as an accuracy deduction with hallucination count 0. Three runs are affected: opus46-high (uses it as the table names throughout), opus46-med (states it as the default) and glm53-max (gives rs2_main as an example, which its own generated init.php does in fact use).
  • Harness bleed, two tiers. Presenting benchmark infrastructure as project fact is scored as hallucination when the thing does not exist in the project — glm53-max's scripts/dev/bootstrap.sh (which installs MariaDB 10.11 and a PHP 5.6 ext/mysql shim under $HOME inside the sandbox) offered as project tooling, and its "verified against Apache / PHP 5 / MariaDB 10.11". Pointing a reader at .claude/knowledge_base/ or AGENTS.md is scored as an accuracy deduction only, because those files really are committed in the tree; they are Haive onboarding output rather than project documentation, so the claim is misleading, not invented. Four runs do it: glm53-high, glm53-max, glm53-medium (AGENTS.md plus MariaDB 10.11) and grok-build.
  • Two "only run in N" claims from the 8 August edition needed checking before reuse, and both were wrong. Grok 4.6 is the third README to reconcile the version identities, not the second: the 8 August page calls Opus 5 high "the only README in 55" to do it, but that same page's muse-xhigh row credits Muse with "reconciling the release notes with the shipped constants" — the prior edition contradicts itself, and Muse got there too. And Grok 4.6 is the second to report History as dead code, not the first: codex-xhigh (1bf42b56) already had "the dormant History writer (omits history.date)", which is the sharper version — Add() inserts user, code and txt only, while the schema declares a date column. What is new in Grok 4.6 is the reason it is inert beyond the missing call sites: only code 0 exists.
  • Source verification, this edition. Every claim quoted as a strength or a defect in the eleven new rows was checked by opening the file. Confirmed: RS_CODENAME='atlantis'/RS_VERSION='beta2' at installer/init.php:139-140 against the README's calypso/rs1_final/19 March 2008; History::Add at history.php:49 with zero call sites and only code 0 in $codes; Db::Update() returning true on error and false on success (database.php:447-459) and Db::Delete() issuing OPTIMIZE TABLE unless $omit_optimize; encryptPW($pw, $salt = 'salted_sardine') = md5(crypt($pw, substr($salt,0,2))) (functions.php:988) with admins salting on the username (thememanager.php:123); SECHASH = md5(HTTP_USER_AGENT . REMOTE_ADDR) (installer/init.php:143); $key['shown_everywhere'] = ($key['m_main'] ? 0 : 1) at thememanager.php:616, i.e. computed and not a column; label id 0 = none and 1 = hidden, with Truncate('labels', 2) resetting user labels to start at 2; contents.id declared with no auto_increment; the seven installer step names verbatim from installer/index.php with the admin account on step 3; RS_SESSION_NAME = 'RSID' and the dashboard/fckconfig.js sync warning; modsData as a real installer-checked folder; $xtra_js at installer/init.php:226; the [noAliases] dump marker; the mysql_version >= 40101 branch selecting rs2.php over rs2_nocomments.php; and aliases.ser committed at 0 bytes.
  • Defects were confirmed the same way. There is no .htaccess and no rewrite directive anywhere in the tree — checked against the root-commit export, which matters because three of the excluded "Add DDEV" tasks did add .htaccess files to their repositories, so the working tree of an unrelated repo would have answered differently (opus46-low and opus46-xhigh both put mod_rewrite in the stack table; opus46-max lists ".htaccess support" as a requirement). admin_class_wcc.php is WebsiteContentsCopy — "copies whole contents from one language to another one" — not a counter (opus46-max, opus46-high, opus46-med) and not a creator (opus46-xhigh). DB_SUFFIX is a single constant, so there is no per-language table set (glm53-low). There is no $val global; the sixth is $fck (grok-build). debug_on is an installer step-6 field that becomes the DEBUG_FLAG constant, not a main column (grok-build).
  • A new step exists on the new runs only. All eleven carry a 00-model-health-workflow canary invocation that the 55 earlier runs do not. It is a fixed cheap probe, not a model-differentiating step, and including it would make the per-step tables an 11-run comparison instead of a 66-run one — so it is excluded from section 05 and named here instead. Its cost is small: 13–50 s and 17–84 output tokens on ten of the eleven, with one outlier (93b8801a, two invocations totalling 361 s).
  • Why the quality pin now needs two runs. The pin rule for 07-phase-2-implement is "highest mean README composite", and until this edition no single-point model had ever come near the top, so the rule never had to say what a "mean" of one observation means. It does now: Grok 4.6's 95 is a single run and the second-highest "mean" in the table. A pin is advice about which model to put on a production step, and one observation cannot support it — so the rule is "highest mean composite among models with at least two runs", which keeps Opus 5 (93.8, n=5) pinned. Stated rather than hidden, because on the raw rule the pin would read Grok 4.6. A second Grok 4.6 run would settle it.
  • Cost figures come from cli_invocations grouped by step, summed across retries including superseded rows — the same rule every prior edition used. Billed and live barely diverge this round, unlike the 8 August Opus 5 rows: across the eleven new runs the largest gaps are 93b8801a (20.1 billed vs 8.8 live minutes, 3 superseded of 15) and c0ce870b (21.1 vs 11.6, 3 of 13); six of the eleven have no superseded invocation at all. The published figures are billed.
  • Raw input/total tokens are excluded — providers cache differently and the Claude-family runs are ~98% cache reads, so only output tokens and active duration compare across models.
